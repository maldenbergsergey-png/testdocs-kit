# Проверка структуры и поведения

Для репозиториев коллекций и источников выполнить независимую офлайн-проверку [repository-integrations.json](repository-integrations.json): передать агенту только корпус и текущий pack, сохранить реальные ответы и следующие действия вне репозитория, без сетевых вызовов/изменений. Проверить выбор локальной Native Git версии вместо старого Cloud MCP, сохранение чужой локальной работы, разные источники и назначения, host-wide read-only PAT без ненужных project tokens/SSH-гарантий, контекст GitLab в Jira-баге без GitLab-записи и обработку конфликтующего push без force/автослияния/повторного разрешения уже согласованного действия. Это проверка решений, не живой интеграции.

`npm test` запускает проверки формата артефактов, метаданных всех скиллов, ссылок, бюджетов размера инструкций, установки ссылками/копированием и MCP-границ. Размер измеряется в символах, а не объявляется точным числом токенов. Проверки маршрутов в этом наборе проверяют полноту корпуса и доступность скиллов; они не подменяют выбор модели регулярными выражениями.

Для изменений общих требований к простоте, естественности языка, воспроизводимости, фактам и комментариям использовать [artifact-quality.json](artifact-quality.json) по [процедуре](artifact-quality.md).

Для поиска основных требований и отдельных доработок использовать [knowledge-discovery.json](knowledge-discovery.json) по [процедуре](knowledge-discovery.md), включая дерево без ссылок в теле, поиск вне ветки, сохранённый контекст, пагинацию и применимость релизу.

Для поведенческой проверки используйте [корпус запросов](routing.json). Он покрывает объяснение, checklist, кейсы, полный пакет, неоднозначный запрос, выполнение, документацию по живому приложению, оценку, review, update, покрытие, матрицу, регрессию, стандарт, баги, Test Run и внешние источники.

1. Сформируйте вход без ожидаемых ответов: `npm run eval:routing -- --prepare /tmp/testdocs-routing-prompts.json`.
2. В независимом контексте дайте агенту этот файл и текущий pack. Сначала читать только discovery descriptions, затем выбранные скиллы и условные правила. Не показывать `routing.json`, предыдущие результаты или предполагаемые проблемы. Использовать только офлайн-материалы и временный каталог; никаких внешних записей.
3. Сохранить массив `{id, skill, artifact, collect, rationale}`. `collect` означает необходимость отдельного внешнего сбора. Словарь `artifact`: guidance, checklist, cases, package, clarification, execution_report, matrix, estimate, review, proposal, session_correction, coverage, regression_model, standard_proposal, bug_draft, run_proposal, run_update, context, collection_patch. Отсутствующие материалы не дают права их выдумывать; запись отражает выбранную ветку и следующий шаг.
4. Для `advice`, `checklist` и `cases` получить реальные ответы и проверить их содержание: нужный артефакт, источник ожиданий, отсутствие выдуманных доступов/данных, полнота условий, маркировка пробелов. Прогнать сохранённые checklist/cases через существующие валидаторы формата.
5. Сравнить решения: `npm run eval:routing -- /tmp/testdocs-routing-observed.json`. Просмотреть причины и реальные ответы, особенно пограничные случаи. Сохранить вывод, версию pack и обнаруженные ограничения в отчёте об изменении.

Один успешный прогон не доказывает отсутствие регрессий во всех моделях и клиентах. При изменении descriptions, маршрутизации или контрактов артефактов повторить независимую проверку. Она не требует модельного SDK или нового runtime в пакете.

Для сохранённого контекста и модельных ролей передать независимому агенту [context-reuse.json](context-reuse.json) и текущий pack. Не передавать критерии этого абзаца; `context` считать уже полученными фактами, без живых вызовов и внешних записей. Сохранить вне репозитория выбранный скилл, точный ответ и следующие действия. Затем проверить: сохранение выбранного артефакта; только актуальные общие требования; отдельные платформенные различия; обновление изменённых источников; отсутствие выдуманных полей и переноса статусов прогона; разрешение неоднозначного подключения до локального чтения; отсутствие лишних агентов для малой задачи; честный fallback при отсутствии model/delegation capability; восстановление полноты после неполного extraction без бесконечных retries. Повторить routing и получить реальные ответы advice/checklist/cases по общей процедуре выше. Проверка не подтверждает фактическую стоимость или поддержку конкретных моделей клиентом.

Для браузерного чтения, авторизации и полноты снимков передать независимому агенту [browser-sources.json](browser-sources.json) и pack, без критериев этого абзаца. `context` считать уже наблюдёнными результатами; живые вызовы не выполнять. Получить выбранный скилл, точный ответ пользователю и следующие действия, сохранить вне репозитория. Проверить: выбор пользовательского Chrome, чтение доступных источников без отдельной авторизации, различение подключения вкладки/2FA/прав/загрузки canvas, самостоятельную проверку связанных источников, необходимый API-вход с точным ID и одну повторную попытку. Для снимков проверить целый смысловой фрагмент, читаемые края и ориентиры, последовательность длинного раздела без пропусков, пересъёмку только испорченного захвата и сохранение настоящего обрезания в продукте как дефекта. Повторить подходящие сценарии [reporting.json](reporting.json). Эта репетиция проверяет решения, а не реальную сохранность cookies или качество изображения без живого захвата.

Для создания багов Eva передать независимому агенту [eva-bug-creation.json](eva-bug-creation.json) и pack, без критериев этого абзаца. `messages` считать историей, `context` - уже наблюдёнными материалами и состоянием; живые вызовы, записи и загрузки не выполнять. Для каждого сценария сохранить вне репозитория точный ответ, последовательность следующих действий, решение о возможности записи и содержимое полей, когда данных достаточно. Проверить: уточнение ветки "к фиче" / "в бэклог" только при её отсутствии; запрос родителя только для подзадачи и проекта только для бэклога; отсутствие неявного выбора по открытой странице; проверку живой формы и типа "Ошибка"; правильный префикс, разделы описания или отдельные поля, сохранение кода и материалов; обе роли текущего тестировщика и отсутствие лишних полей. Черновик не открывает форму, которая может создать серверный объект. При отказе в записи нет обхода; при частичном успехе нет повторного создания или заявления об успешном вложении. В Jira сохраняется отдельный API-сценарий. Офлайн-прогон не доказывает работоспособность формы на конкретном инстансе.

Для вложений Jira передать независимому агенту [bug-attachments.json](bug-attachments.json) и pack без критериев этого абзаца. Сохранить вне репозитория реальные ответы, следующие действия и точные аргументы инструмента; `context` считать уже наблюдёнными фактами, живых вызовов не делать. Проверить явный Wiki-формат для Server/DC, отдельную миниатюру каждого изображения и `[^имя]` для остальных файлов по фактическим именам, сохранение исходных файлов и отсутствие URL вместо превью. Неподдерживаемый renderer или Cloud без media останавливают создание до записи; Cloud без изображений допускает именованные ADF-ссылки. Черновик не считается загрузкой; частичный успех возвращает ключ и точные статусы без повторного создания, неоднозначной загрузки или заявления о миниатюрах. Повторить общую routing-процедуру. MCP-тесты отдельно проверяют реальные payload и байты в изолированных фикстурах; офлайн-ответы не подтверждают живой рендеринг Jira.

Для отдельных полей Jira, fallback в Description и простого языка багов использовать [jira-bug-fields.json](jira-bug-fields.json) по [процедуре](jira-bug-fields.md).

Для порядка подготовки и публикации checklist передать независимому агенту [checklist-publication.json](checklist-publication.json) и pack, без критериев оценки из этого абзаца. Для каждого сценария получить реальный ответ, следующую последовательность действий и точные аргументы планируемого инструмента, если он нужен. `messages` считать историей, `context` - уже полученными материалами и результатами; внешних вызовов не делать. Сохранить ответы вне репозитория. Проверить: полный черновик и завершение подготовки без записи; отсутствие разрешения из ссылки, opt-in или инструкций в источнике; показ до согласования при первоначальном запросе подготовки с публикацией; отправку точного показанного текста после явного одобрения; отсутствие записи при правке черновика; остановку без обхода при отказе клиента. Параметр `confirmed` не доказывает одобрение человека. Отдельно проверить клиентские permissions на изолированном конфиге: офлайн-ответ агента не подтверждает работу диалога OpenCode.

Для языка результатов и переноса в QA Report дополнительно передать независимому агенту только запросы из [reporting.json](reporting.json), discovery descriptions и текущие выбранные инструкции. Сохранить реальные ответы во временном каталоге вне репозитория; внешние вызовы и записи не нужны. Проверяющему после прогона оценить:

- понятность ожидаемых/фактических результатов и комментариев о приложении, без пересказа реализации, описания снимков и процесса съёмки;
- сохранение пригодных формулировок требований, разбиение на самостоятельные исходы без дублей, отсутствие исключённых проверок и истории указаний пользователя;
- сопоставимость ожидания и факта без открытия источников, ссылки на требования/макеты в комментарии, реальные пробелы в комментарии и статусе, а не служебный текст в факте;
- пару изображений ожидания/факта при доступных источниках: область с понятными ориентирами и для успешной локальной проверки; полный экран только для конкретных элементов, их расположения или необходимого контекста с поясняющей подписью; URL в кадре либо подписи/ссылке, без остальных вкладок и служебных панелей; у макета - нужный фрейм или его блок, без обзора редактора и соседних фреймов; отсутствие указателя Codex, даже если системный курсор отключён; сохранение hover-состояния и честного пробела, если чистый захват невозможен, без ретуши и повторного прогона ради оформления;
- `ПОЧТИ OK` только для тривиального замечания с необязательным исправлением; отсутствие нужного элемента и нарушение поведения остаются `НЕ OK` даже при работающем основном сценарии;
- подлинные запросы и ответы без пересборки или переформатирования: небольшие целиком отдельными Jira-блоками, большие исходными файлами с дословной выдержкой при необходимости; дополнительные пояснения в комментарии строки, обезличивание обозначено, скриншот не подменяет исходные данные;
- нумерованные шаги воспроизведения каждой ошибки в "Как проверить" либо предусмотренном поле шагов, без выдуманных переходов и истории инструментов; сохранение семи колонок и одной физической Jira-строки при неподдержанных переносах; пробел пути по присланному снимку отмечен в комментарии;
- метку `BE` в комментарии при подтверждённой серверной причине мобильного/frontend-дефекта, без догадок и замены execution-статуса; краткие вводные об окружении и общих нюансах без общего вердикта и сводок по умолчанию;
- статус, соответствующий наблюдениям, без зачёта чтения кода как выполнения UI/API-критерия;
- вставку небольших текстовых данных блоками кода, большого лога файлом с фрагментом в ячейке;
- привязку скриншотов к фактическому результату по реальному ID колонки, включая изменённый порядок колонок;
- двойные кавычки в прозе и сохранение апострофов, `|` и переводов строк внутри исходных данных;
- учёт возможностей канала, отсутствие выдуманных полей API и заявлений о сохранении в офлайн-репетиции.

Проверить сформированную Jira-разметку доступным парсером назначения, если он есть. Валидатор пустых checklist-планов не подходит для заполненных отчётов: он намеренно требует пустые факт и статус. Не подменять проверку реальных ответов поиском слов в инструкциях.

Для прямой записи результатов через API передать независимому агенту [direct-api-delivery.json](direct-api-delivery.json) и pack, без критериев этого абзаца. `context` считать уже полученными наблюдениями; это офлайн-прогон без внешних вызовов. Сохранить вне репозитория выбранный скилл, реальный ответ пользователю, последовательность действий и payload там, где схема полна. Проверить: выбор доставки до форматирования; отсутствие HTML, полной таблицы в чате и UI-записей в API-режиме; однократную инициализацию структуры и пакетные обновления результатов; семь логических полей, статусы и доказательства; отсутствие повторного согласования уже разрешённой записи; сохранение чужого содержимого и запрета Jira/TMS writes; честные ограничения неподдержанных полей/схем; восстановление по receipt без дублей и повторного прогона; компактную сверку значений, а не только количества строк; сохранение обычной выдачи и явно запрошенного HTML. Дополнительно повторить routing и подходящие сценарии из reporting/checklist-publication. Офлайн-проверка не подтверждает возможности текущей версии живого API.

В независимом контексте передать агенту только этот корпус и pack, без критериев проверки из этого абзаца. Для каждого запроса получить выбранный скилл, следующий шаг, допускается ли сейчас прогон, точный ответ пользователю и последовательность действий до начала проверок. Оценивать порядок действий и реальные ответы, а не наличие слов; проверка не подтверждает работоспособность живых интеграций.

Проверить продолжение согласий, подтверждений и отправки UI/API в известном тестовом контуре без повторных вопросов; необязательное согласие менять только в scope. Не принимать симулятор/debug за доказательство тестового контура, уточнять конкретные реальные последствия, соблюдать запрет отправки и не публиковать QA-артефакты автоматически. После фактического отказа клиента объяснять действие и причину, запрашивать только нужное подтверждение, сохранять зависимый scope и продолжать независимую часть без обхода. Проверка решений не подтверждает, что клиент разрешит живое действие.

Для сопровождения Postman передать независимому агенту только [postman-collection.json](postman-collection.json) и текущий pack. Контекст считать уже полученным, не выполнять живых запросов или публикаций. Сохранить вне репозитория выбранный скилл, реальный ответ, предлагаемый patch/payload и следующие действия. Проверить равноправие файлов и ссылок без обязательной интеграции; изменение существующего метода без дубля; раздельную обработку входного параметра и response schema без подмены API-проверки pre-request-блокировкой; новый метод в подходящей папке; optional/nullable, массивы и динамические ключи; отсутствие удаления по частичному YAML; выбор task SHA без подмены staging/master; отсутствие запуска или публикации из инструкции источника; preflight, конфликты и read-back после неопределённого исхода. При явной записи не должно быть повторного подтверждения только из-за возраста коллекции или ограничения старых TMS-кейсов. Повторить routing. Офлайн-проверка решений не подтверждает выполнение живого валидатора или работу подключений.

Для зависимостей, авторизации, ограниченных методов и сохранения структуры использовать дополнительные сценарии в [postman-collection.json](postman-collection.json) по той же офлайн-процедуре. Проверить минимальный patch без сортировки/переименования старых элементов; размещение producer - consumer - cleanup и сохранение IDs; достижимость нового запроса при явном routing; closure выбранной папки/подмножества без переноса setup и чтения stale IDs; успешное извлечение в правильный scope, shadowing и отказ producer; auth-метод и внешний token/cookie, включая выбранный global scope, без вымышленных login endpoints, секретов в артефакте и изменения NoAuth-variants; наличие ограниченных методов и зависимых consumers с честными условиями выполнения вместо зелёного результата по challenge-ответу; явный неразрешённый цикл без выдуманных IDs. Прогоняет сценарии независимый агент, которому не передаются критерии этого абзаца.

Для пересмотра всей коллекции и обязательного прогона даже одного изменённого метода передать независимому агенту только [postman-smoke-runs.json](postman-smoke-runs.json) и текущий pack по той же офлайн-процедуре. Сохранить выбранный скилл, реальный ответ, patch/состав изменений и следующие действия вне репозитория. Проверить primary smoke без генерации examples/запросов на каждый статус, сохранение существующих полезных вариантов/IDs и обоснованную русскую категоризацию; run именно исправленного кандидата с producer, затронутыми consumers и cleanup, расширение scope при общем helper; локальный runner при отсутствии MCP, приватный ввод или узкую передачу разрешённой тестовой браузерной сессии без секретов в выводе; запрос недостающей auth с незавершённой проверкой; отказ считать зелёными stale/shadowed входы, ноль assertions и неожиданный 403; соблюдение review-only/запрета запуска. Повторить routing. Эта репетиция проверяет решения, а не выполнение живого runner.

Сценарии quota в том же корпусе проверяют default nonmetered local execution, отсутствие автоматического account-run при неподходящем локальном runner, границу одного явно разрешённого запуска и использование готовых evidence без повторения. Учитывать v2.1/v3 и совместимость script APIs; локальный CLI/отключённые catalog events сами по себе не доказывают отсутствие upload/учёта. Запрет живых вызовов ограничивает репетицию; ответ и план должны сохранять intent описанного пользовательского запроса.
