# Проверка кратких вводных

При изменении вводных QA Report выполнить независимую офлайн-проверку по [report-introduction.json](report-introduction.json) и текущему pack. Передать агенту только запросы корпуса и discovery descriptions, затем дать прочитать выбранные инструкции. Не передавать этот файл с критериями. Получить реальные ответы для всех сценариев; сохранить их и оценку вне репозитория. Не выполнять внешние вызовы или запись отчёта.

После прогона проверить:

- В поле стенда только подтверждённая категория или короткое имя; URL, клиент, сборка и размеры туда не попадают. Стартовый STAGE не выдаётся за факт.
- Во вводных обычно 1-2 короткие строки: клиент и существенное общее ограничение. Нет описания задачи, даты/хода прогона, дефектов, итога, счётчиков, списка источников и исключённого scope. Частный пробел остаётся в строке.
- У мобильного клиента сохраняются платформа, известные ОС/сборка/устройство и тип/размер симулятора с единицами, без второго размера в пикселях скриншота. Не добавляются неизвестные значения.
- Последняя версия браузера допускается по явному соглашению пользователя; известная фактическая версия имеет приоритет. Без соглашения версия не выдумывается и не запрашивается только ради вводных.
- План не выдается за выполненный прогон. При неподдержанных полях API значения подготовлены, ограничение доставки обозначено отдельно; нет выдуманного payload или UI fallback.
- Нужная ссылка на нестандартный стенд сохранена одной именованной ссылкой, не в поле стенда. Ограничения сокращены без потери существенной границы покрытия.

Проверить смысл и объём реальных ответов, а не только наличие слов в правилах. Выполнить `npm test` для структурной проверки; офлайн-репетиция не доказывает сохранение или отображение полей живого QA Report.
