# Сценарии использования

## Основные сценарии использования

Команды формулируются обычным языком. Достаточно указать требуемый результат и дать ссылку, ключ, документ или сами требования.

### Мобильные приложения: Maestro MCP

Для проверки задачи агент получает контекст, показывает checklist, затем выполняет проверки и возвращает отчёт в чате. Платформу выбирает из задачи: iOS - Simulator на macOS, Android - эмулятор Android Studio, web и mobile web - браузер. Переданную готовую сборку использует без повторной установки или подтверждения. Если устройство не запущено, просит запустить его и открыть приложение; если среда или управление недоступны, использует скринкасты/скриншоты с явной отметкой источника и непроверенной части.

Для управления нужны Maestro CLI, Java 17+ и подготовленная среда Android Studio/Android SDK либо Xcode с Simulator. Открытая IDE сама по себе не означает готовое устройство. [Подключение и ограничения](../integrations/profiles/maestro.md).

| Пример запроса | Результат |
| --- | --- |
| "Протестируй iOS-задачу TASK-123, нужная сборка уже открыта в Simulator" | Checklist по задаче, проверки в Simulator, отчёт и сохранённые доказательства, включая успешные проверки |
| "Быстро проверь фильтры в Android: Каталог / Фильтры; требования: …" | Короткий checklist и фактические результаты только по компоненту; ключ задачи необязателен |
| "Построй матрицу по каталогу в открытом приложении" / "Напиши кейсы по требованиям и этому экрану" | Запрошенный артефакт с наблюдаемой структурой и путями; требования определяют ожидаемое поведение |
| "Перенеси результаты со скриншотами в QA Report, вот временное API-подключение" | Сохранённый отчёт и файлы этого прогона по [профилю QA Report](../integrations/profiles/qa-report.md) |

При настройке/обновлении kit режим `auto` подключает найденный CLI как `testdocs_maestro`. Без CLI остальной набор продолжает работать. После установки Maestro выполните из установленной копии kit:

```bash
npm run configure:maestro -- --maestro-mode auto
npm run check:maestro
```

Перезапустите AI-клиент и дайте задачу с требованиями, сборкой и app ID. Команда проверки подтверждает только запуск CLI; доступ к устройству и приложению агент проверяет отдельно. Отключение: `npm run configure:maestro -- --maestro-mode off`. SDK и эмуляторы установщик kit не скачивает. Изменения в development checkout не обновляют действующую установку.

### Оценить трудозатраты QA

```text
Оцени трудозатраты QA на эти задачи в человеко-часах: <описания или ссылки>.
Учти документацию, регрессию, ретест и применимые платформы.
```

Результат: краткий блок для комментария по каждой задаче или подзадаче: границы, часы по частям и стендам, базовая оценка, резерв и итог. Агент изучает головную историю, связанные задачи и материалы, сохраняя отдельные границы каждой оценки. Общие работы пакета учитываются один раз, прогоны iOS и Android раздельно. Можно запросить пересчёт, сравнение с фактом или минимальный состав выпуска с бизнес-ценностью. Явный вызов - `$qa-task-estimation`.

Включены [профиль процесса](../rules/qa-estimation-profile.md) и [матрицы платформ](../rules/qa-estimation-platform-matrix.md): основное тестирование Dev, кросс-проверка коллегой, регрессия Stage, доступный smoke Prod, документация и финальная валидация человеком при помощи ИИ. Матрицы различают базовое и дополнительное покрытие; ширины из примеров не заменяют макеты конкретной задачи. Исторические 25-30% от разработки не являются формулой расчёта. Нормативов часов пока нет, поэтому экспертные оценки остаются предварительными. Проектные дополнения хранятся по [правилам команды](../rules/qa-estimation-team-rules.md). [Проверочные сценарии](../examples/workflows/qa-task-estimation.md) содержат учебные данные, не нормативы.

Навык находится в `skills/qa-task-estimation/` и подхватывается существующим установщиком вместе с остальными skills. Разработка в checkout не обновляет развёрнутые клиентские установки.

### Как протестировать задачу

```text
Изучи TASK-123 и объясни понятным языком, как её лучше протестировать.
```

Результат: практическое объяснение подготовки, действий, наблюдений, рисков и диагностических материалов. Checklist и Test Cases не создаются без отдельного запроса.

### Выполнить тестирование

```text
Протестируй реализацию TASK-123 на STAGE и подготовь отчёт.
```

Агент собирает контекст, показывает рабочий checklist, выполняет доступные web/Android/iOS/API/integration проверки и сравнивает интерфейс с переданным макетом. Результат - Jira Wiki отчёт в чате с фактами, доказательствами и ограничениями. Перенос в QA Report или Jira выполняется по отдельному запросу.

### Браузер для выполнения UI-проверок в OpenCode

Подключить официальный локальный Playwright MCP:

```bash
npm run configure:browser
```

Выберите `persistent` (отдельное окно установленного Google Chrome, вход сохраняется), `extension` (текущая вкладка Chrome/Edge через [официальное расширение](https://github.com/microsoft/playwright/tree/main/packages/extension)) или `off`. По умолчанию браузер выключен; включение не меняет разрешения на записи в Jira/TMS.

Для применения сохранённых настроек без вопросов:

```bash
npm run setup -- --reuse --browser-mode persistent
```

Установщик добавит `testdocs_browser`, установит закреплённую версию `@playwright/mcp` и проверит наличие браузерных инструментов. После установки перезапустите OpenCode и выполните `opencode mcp list`. Для V2 используйте `opencode2 mcp list`; формат установщик определяет автоматически, доступен `--opencode-format stable|v2`.

Пример запроса: `Открой <URL тестового стенда> через testdocs_browser, проверь авторизацию и выполни проверки задачи. Если нужен вход, открой форму и дождись моего входа в браузере.`

В режиме `persistent` личные cookies не копируются: один раз войдите в открывшемся Chrome. Профиль хранится в пользовательском data directory Testdocs Kit, отдельно от репозитория. Один профиль используется одним прогоном одновременно. В режиме `extension` установите расширение и разрешите подключение к нужной вкладке; токен расширения в чат или конфиг kit не нужен.

Локальный браузер работает в сети компьютера, где запущен MCP, включая доступный ему VPN. Удалённый OpenCode запускает браузер на удалённом хосте. Ошибка текстового Webfetch не является проверкой доступа из этого браузера. Успешный MCP handshake подтверждает инструменты, но не вход и доступность конкретного стенда.

Документация: [OpenCode MCP](https://opencode.ai/docs/mcp-servers/), [Playwright MCP](https://github.com/microsoft/playwright-mcp).

### Figma в OpenCode

Из установленной копии kit выполните:

```bash
npm run configure:figma
```

По умолчанию команда включает **browser**: агент открывает Figma через `testdocs_browser`, использует обычный доступ к файлу и делает снимки макета. Платный Dev Mode, Figma Desktop MCP, OAuth Figma MCP и API-токен для этого режима не требуются. Старое официальное MCP-подключение Figma убирается, остальные интеграции сохраняются. Установленный браузерный режим (включая extension) сохраняется; если его нет, используется отдельный Chrome с сохраняемым входом. Для работы с canvas включаются инструменты скриншотов и координатных действий Playwright.

После настройки перезапустите OpenCode. Попросите агента открыть ссылку на конкретный frame через `testdocs_browser` и войдите в Figma в открытом браузере, если требуется. Экспорт возможен только при разрешении владельца файла. Снимок подтверждает видимое оформление, но не скрытые свойства, переменные или точные размеры слоёв. Для чтения canvas модель/клиент должны уметь просматривать изображения; если это недоступно, передайте экспортированный PNG или другой доступный материал и явно ограничьте объём проверки.

`opencode mcp list` покажет `testdocs_browser`, а не отдельный `testdocs_figma`. Состояние MCP не подтверждает вход в Figma и доступ к конкретному макету. Обычный `npm run update` сохраняет выбранный режим; для переключения старой настройки выполните `npm run configure:figma` один раз. Отключение Figma не отключает общий браузер, который нужен и для тестирования приложения.

Дополнительные режимы выбираются явно:

```bash
npm run configure:figma -- --figma-mode desktop
npm run configure:figma -- --figma-mode remote
npm run configure:figma -- --figma-mode off
```

**Desktop** требует доступа к desktop MCP в Figma (Dev/Full seat на поддержанном платном плане): откройте макет в приложении, включите Dev Mode → Enable desktop MCP server и оставьте Figma открытой. **Remote** использует облачный OAuth, поддержку клиента со стороны Figma и лимиты плана; его нельзя обещать как неограниченный бесплатный вариант. REST API с персональным токеном также имеет лимиты и не является способом их обойти. Режим browser использует только разрешённые обычному пользователю действия и не обходит ограничения файла.

Источники: [права просмотра и экспорта](https://help.figma.com/hc/en-us/articles/15297425105303-Explore-design-files), [доступ к Figma MCP](https://developers.figma.com/docs/figma-mcp-server/plans-access-and-permissions/), [лимиты REST API](https://developers.figma.com/docs/rest-api/rate-limits/).

### 1. Чек-лист для задачи

```text
Подготовь чек-лист для тестирования: https://jira.example.test/browse/TASK-123
```

Результат: только готовый checklist в Jira Wiki Markup. Агент читает задачу и релевантные связанные материалы, но не запускает полный анализ постоянного TMS-покрытия.

### 2. Вся тестовая документация для задачи

```text
Подготовь всю тестовую документацию для TASK-123.
```

Результат: краткий scope, Jira checklist и необходимые новые или актуализированные Test Cases. Вывод содержит только полезные разделы, без внутренней маршрутизации и пустых отчётов.

### 3. Чек-лист или кейсы по документу

```text
Подготовь чек-лист по этому документу: https://confluence.example.test/pages/viewpage.action?pageId=12345
```

```text
Напиши тест-кейсы по приложенному документу.
```

```text
Сопоставь требования этого документа с существующими тест-кейсами и покажи пробелы покрытия.
```

Jira-задача необязательна. Источником может быть Confluence, PDF, DOCX, локальный файл или требования в сообщении.

### 4. Тест-кейсы для задачи

```text
Напиши тест-кейсы для TASK-123.
```

Результат: только кейсы в указанном scope. Агент не объявляет их частью регрессионной модели без отдельного запроса.

Если кейсы нужны только для текущего изменения:

```text
Напиши тест-кейсы только для проверки TASK-123. В регрессионную модель их не включать.
```

В таком режиме допускаются task-specific и разовые сценарии, поддержанные требованиями.

### 5. Только определённая часть задачи

```text
Для TASK-123 напиши тест-кейсы блока «Фильтры».
```

Агент не расширяет ответ до полного пакета и добавляет только обязательные зависимости запрошенного блока.

### 6. Оптимизация существующих кейсов

```text
Оптимизируй приложенные тест-кейсы и приведи их к текущим правилам. Убери дубли, но сохрани покрытие.
```

Результат: замечания, целевая структура и полные исправленные proposals. Изменения не записываются в TMS автоматически; дубли предлагаются к выводу из актуального покрытия, а не удаляются.

### 7. Ревью кейсов

```text
Проведи ревью PROJECT-T123 и PROJECT-T124.
```

Результат: статус, конкретные замечания и полная исправленная proposal-версия, когда изменения действительно нужны.

### 8. Актуализация и применение

```text
Актуализируй PROJECT-T123 с учётом следующего изменения: ...
```

Эта команда готовит diff и полную proposal-версию без записи. Следующая команда применима только к кейсу, который текущий MCP-процесс создал в этой сессии. Для остальных кейсов агент возвращает предложение для ручного применения:

```text
Примени предложенные изменения в PROJECT-T123.
```

### Дополнительные действия

Свободное или надиктованное описание можно превратить в черновик:

```text
Составь баг-репорт: на странице оформления после удаления промокода итоговая сумма не пересчитывается...
```

По точной версии релиза можно подготовить Test Run с ограничением поиска заданной папкой Zephyr:

```text
Собери рекомендуемый Release Regression для версии 2.14.0, WEB, папка Regression/Web. Распредели кейсы между Анной и Олегом.
```

Сначала используются кейсы, связанные с задачами релиза. Для задач без подходящих связей выполняется смысловой поиск по полному содержимому всех кейсов только в указанной папке. Формулировка `собери` возвращает proposal; для создания Test Run и связанной QA-задачи нужен явный запрос `создай` или `заведи`.

Для создания в Jira нужен явный create-запрос и проект:

```text
Заведи этот баг в проекте SHOP. Назначь на меня, остальные необязательные routing-поля не угадывай.
```

Перед созданием агент читает живую схему полей проекта. Если Jira содержит отдельные поля для шагов, ожидаемого и фактического результата, используются они; иначе блоки попадают в структурированное `Описание`. Агент также добавляет подтверждённые ссылки на требования и макеты, точное окружение/URL и релевантные диагностические материалы. Для визуальных, поведенческих, backend и mobile-дефектов состав доказательств различается; секреты и персональные данные в запросах и логах маскируются.

В Eva сначала выбирается, относится ли баг к фиче или должен попасть в бэклог. Если выбор не указан, агент уточняет его. Для фичи нужна родительская задача, для бэклога - проект:

```text
Создай в Еве баг подзадачей MOBILE-42: iOS, в профиле после сохранения остаётся старое имя вместо нового. Прикрепи этот скриншот.
```

```text
Заведи в бэклог проекта MOBILE в Еве баг: Android, в профиле после сохранения остаётся старое имя вместо нового.
```

В обоих случаях используется тип "Ошибка", исполнитель и постановщик - текущий тестировщик. Заголовок начинается с "iOS. " или "Android. " и описывает что, где и когда сломалось. В описании оформляются шаги, ожидаемый и фактический результат, когда отдельных полей нет; прикладываются доступные снимки, фрагменты кода и другие относящиеся к багу материалы. Необязательные поля не заполняются. Создание выполняется через живую форму в подключённом браузере, для бэклога в том числе через хедер. Встроенный Eva MCP предоставляет только чтение. Подключение и порядок работы описаны в [профиле Eva](../integrations/profiles/eva.md#browser-creation-workflow). Запрос "составь черновик" ничего не создаёт и не открывает форму создания.

```text
Опубликуй подготовленный checklist комментарием в TASK-123.
```

```text
Отправь checklist в QA Report и открой редактор в отдельной вкладке.
```

При отправке в QA Report агент по умолчанию учитывает известную ссылку на задачу и стенд из контекста, включая точный URL стенда. Промпт временного API из открытого отчёта выбирает отдельный канал, который поддерживает текст и бинарные вложения. Поля задачи и окружения заполняются по возможностям этого канала и проверяются отдельно; если API не поддерживает поле, агент использует доступный внешний редактор или сообщает, что осталось заполнить. Контракт и ограничения описаны в [профиле QA Report](../integrations/profiles/qa-report.md).

Для временного API отдельный MCP не обязателен: агент может выполнить запросы через доступный HTTP-инструмент, Node.js, Python или `curl`. Выданный пользователем временный токен разрешено использовать для указанной сессии без повторного запроса; способ передачи и защита от вывода секрета описаны в профиле. Ответ `status: "saved"` при чтении конкретного пакета подтверждает сохранение независимо от выбранного HTTP-клиента. Отсутствие отдельного MCP не является основанием заменять запрос на текстовый импорт без файлов.

Новый пустой шаблон с двумя строками-подсказками и стандартными `STAGE` / `OK` заполняется по запросу без дополнительного вопроса о замене отчёта. Эти значения не подтверждают стенд или успешное тестирование; реально введённые данные отличаются от подсказок и сохраняются в пределах запроса.

Во время UI-тестирования агент сразу сохраняет скриншоты результатов, включая успешные `OK`, и связывает файлы со строками чек-листа в workspace задачи. Поздний запрос «прикрепи скриншоты в QA Report» использует сохранённые файлы этого прогона без повторного прохождения функционала. Повторный захват нужен только для конкретного отсутствующего или неподходящего доказательства либо нового прогона. Если пользователь публикует в Jira сам, работа агента заканчивается сохранением чек-листа со скриншотами в QA Report.

Если пользователь называет конкретный артефакт — чек-лист, тест-кейсы, coverage-анализ или баг-репорт — агент возвращает именно его. Только явное «Подготовь всю тестовую документацию для …» или «Подготовь полный пакет …» запускает checklist и Test Cases вместе. Неоднозначное «Подготовь тестирование …» не расширяется до всех артефактов молча. Формулировки «не для регресса» и название конкретного блока дополнительно ограничивают scope. Jira, Confluence и TMS необязательны: те же сценарии работают с текстом и файлами, переданными вручную. Подробнее — в [описании workflows](workflows.md).
