# Пользовательские workflow

Пользователь формулирует QA-задачу обычной фразой. Имена skills и последовательность интеграций знать не нужно.

## Выбор workflow

Агент выбирает ветвь по ожидаемому результату, а не по типу ссылки:

| Запрос | Результат |
| --- | --- |
| `Подготовь чек-лист ...` | Только Jira Wiki checklist |
| `Подготовь всю тестовую документацию ...` | Checklist и постоянные Test Cases/proposals |
| `Напиши тест-кейсы ...` | Только запрошенные кейсы; regression membership не назначается автоматически |
| `...только для задачи, не для регресса` | Task-scoped кейсы вне постоянной модели |
| `...только для блока X` | Только указанный scope и его обязательные зависимости |
| `Оптимизируй эти кейсы ...` | Review набора и структурный refactoring proposal |
| `Проведи ревью ...` | Review без внешней записи |
| `Составь баг-репорт ...` | Jira-ready черновик без внешней записи |
| `Заведи баг в проекте ...` | Один Bug или defect subtask после проверки live Jira metadata |

Источником может быть Jira issue, Confluence page, отдельный документ, файл или текст в чате.

Компания и Jira-проект всегда изолированы. Названия окружений, URL, issue types, custom fields, компоненты, метки, направления и правила назначения берутся только из текущего явно заданного проекта и не переносятся между подключениями.

## Баг-репорт

`Составь баг-репорт по моему описанию: ...` возвращает заголовок, шаги, фактический и ожидаемый результат, окружение и релевантные материалы. Jira не изменяется.

`Заведи этот баг в проекте DEMO.` явно разрешает создание одной задачи. Агент сначала читает live create metadata выбранного проекта, определяет поддерживаемый Bug/subtask type и раскладывает данные по фактически доступным полям. Если отдельных полей нет, используется структурированное `Описание`.

Если пользователь ссылается на требования, аналитику, макеты или логи, агент добавляет прямые именованные ссылки только из переданного или явно ограниченного контекста. Визуальные, поведенческие, backend и mobile-дефекты получают разные релевантные материалы. Внутренние домены и правила одного проекта не сохраняются в переносимом наборе и не используются в другом проекте.

## Чек-лист задачи или документа

`Подготовь чек-лист для тестирования DEMO-123.`

Агент собирает описание, acceptance criteria, связанные документы и релевантные комментарии, затем возвращает Jira Wiki checklist. Вместо Jira key можно передать Confluence URL, документ, файл или требования в чате. Предыдущий чек-лист тестировщика в комментарии используется как дополнительный практический источник, а не как единственная истина: его проверки сверяются с актуальными требованиями, а переиспользованные строки получают пометку источника в колонке `Комментарий`. Разделы и строки группируются по смыслу и способу выполнения без лишнего дробления; разные роли, состояния и самостоятельные outcomes остаются отдельными. `Требует уточнения` появляется только при реальной неоднозначности. Полный поиск постоянного TMS-покрытия не выполняется без отдельной необходимости.

## Полный пакет

`Подготовь всю тестовую документацию для DEMO-123.`

Это явный запрос полного пакета: краткий scope, task checklist, targeted поиск существующих cases, решения «Создать / Актуализировать / Сделать неактуальным / Без изменений / Требует уточнения», полные новые cases и полные update proposals.

Пустые аналитические разделы не выводятся. Если постоянное покрытие менять не нужно, агент сообщает это одной строкой.

## Test cases

`Напиши тест-кейсы для DEMO-123.`

Агент возвращает только кейсы в заданном scope. Без явного запроса на регрессионное покрытие он не назначает suite membership и не утверждает, что кейсы входят в постоянную модель.

`Напиши тест-кейсы только для проверки DEMO-123. В регрессионную модель не включать.`

Этот режим допускает поддержанные задачей временные и разовые сценарии. Перед кейсами добавляется одна короткая отметка о task-only scope.

## Точечный scope

`Для DEMO-123 напиши только кейсы блока «Фильтры».`

Агент не создаёт checklist, полный пакет или кейсы соседних блоков. Общий базовый кейс и админская настройка добавляются только как обязательные зависимости согласно правилам.

## Оптимизация набора

`Оптимизируй эти кейсы и приведи их к текущим правилам.`

Агент сравнивает набор целиком, предлагает общий базовый кейс для одинаковой логики, delta-only варианты для поддержанных текущим проектом направлений, объединение механических дублей и разделение перегруженных cases. Результат остаётся proposal; существующие cases не изменяются и не удаляются автоматически.

## Конкретный case и review

`Актуализируй DEMO-T123 с учётом требования ...` возвращает focused diff и полную предлагаемую версию без записи. `Проведи ревью DEMO-T123` возвращает статус, замечания и исправленную полную proposal-версию, если изменения нужны.

## Применение

`Применить предложенные изменения в DEMO-T123.` — отдельное разрешение записи. Перед PUT коннектор заново читает case и сравнивает его с baseline proposal. При расхождении запись не выполняется. Удаление, автоматический retire, status transition, move, comment и link этим workflow не выполняются.

## Публикация checklist

`Опубликуй подготовленный checklist комментарием в DEMO-123.` отправляет точную показанную Jira Wiki разметку через отдельный разрешённый tool. Автором комментария становится пользователь, чьи Jira credentials настроены в Testdocs Kit. Генерация checklist сама по себе публикацию не разрешает.

`Отправь checklist в QA Report и открой редактор.` вызывает документированный import API, получает временный editor URL и открывает его отдельной вкладкой, если клиент умеет управлять браузером. Встроенный iframe не используется; без browser capability возвращается кликабельная ссылка.

## Без интеграций

Те же workflows работают по требованиям и cases, переданным в чат или файлами. Недоступность Jira, Confluence или TMS фиксируется отдельно и не превращается в выдуманное отсутствие требований или покрытия.
