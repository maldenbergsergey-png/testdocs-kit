# Решение проблем установки

## Если что-то не работает

### `npm run setup` не запускается

Проверьте:

```bash
node --version
npm --version
```

Требуется Node.js 20 или новее.

Если Windows PowerShell блокирует `npm.ps1` из-за политики выполнения сценариев,
запустите тот же npm launcher напрямую:

```powershell
npm.cmd run setup
```

Если настройки уже были сохранены предыдущей попыткой, используйте
`npm.cmd run setup -- --reuse`, чтобы не вводить их повторно.

### OpenCode сообщает `Unrecognized key: permissions`

Эту ошибку создавала версия Testdocs Kit 0.2.0 при установке в стабильный OpenCode. Обновите репозиторий и повторите настройку:

```bash
git pull
npm run setup -- --clients opencode
```

Установщик удалит только добавленное им несовместимое поле, перенесёт свои MCP-серверы в правильный раздел и проверит конфиг через `opencode debug config`.

### MCP не отображается

1. Выполните `npm run check`.
2. Полностью перезапустите AI-клиент.
3. Проверьте MCP-командой из таблицы выше.
4. Если репозиторий перемещался, повторите `npm run setup`.

### Ошибка `401`

Неправильный логин, пароль, токен или режим авторизации. Повторно выполните `npm run setup` и выберите правильный тип установки.

### Jira или Confluence запрашивает 2FA для каждой задачи или страницы

Обновите проблемную установку командой `npm run update` и полностью перезапустите AI-клиент. Ранее вариант "логин и пароль" отправлял Basic с каждым запросом, а браузерная сессия не сохраняла обновления cookies из ответов сервера. Теперь пароль используется только при получении первой сессии, а cookies обновляются и переиспользуются. API-токены и PAT работают по-прежнему.

Для SSO/2FA без API-ключей выберите вариант "вход через браузер/SSO/2FA" в `npm run configure:jira` / `npm run configure:confluence`. При `AUTH_REQUIRED` выполните точную команду из ошибки с ID подключения, например `npm run auth -- jira jira-2`, подтвердите вход и повторите исходное чтение один раз. Команда поддерживает также подключения по логину и паролю. Не добавляйте `--force`, если обычная проверка сессии успешна.

После отказа авторизации адаптер останавливает последующие запросы этого подключения, включая дочерние задачи, до восстановления сессии. Обычный `403`, сбой VPN, TLS или сети сам по себе не требует нового входа. Если уведомления продолжаются после обновления, для Jira проверьте `jira_get_connection_diagnostics`: `connection.sessionReuse` должен быть `browser` или `password`, а `runtime.sourceRoot` и отпечаток кода должны относиться к обновлённой копии. `none` соответствует токенам либо Basic без включённого переиспользования сессии.

Если сервер требует новую 2FA даже при передаче актуальных cookies, сохраните время и безопасный `HTTP diagnostics` одного отказа для администратора. Не присылайте пароль, cookies или содержимое session-файла. Политика привязки сессии к браузеру или обязательной повторной проверки может потребовать чтения через уже авторизованный браузер.

### Ошибка `403`

Ответ может означать недостаток прав на ресурс или отказ со стороны прокси/SSO-шлюза. Сравните один и тот же URL, токен и режим авторизации; для Server/DC PAT нужен Bearer. `npm run check` проверяет запуск MCP и список инструментов, но не доступ к данным.

Если после обновления и перезапуска клиента блок диагностики всё равно не виден, попросите вызвать `jira_get_connection_diagnostics` без параметров и показать его результат. Этот локальный read-only инструмент возвращает `runtime.sourceRoot`, время загрузки, версию пакета, отпечаток кода, выбранное Jira-подключение и наличие `X-Sp-Secret`. `lastHttpError` содержит последний диагностический блок этого процесса, поэтому создание кейса повторять не нужно. `null` означает, что в этом процессе ещё не сохранена HTTP-ошибка; после перезапуска история не переносится. Инструмент не обращается к Jira и не проверяет права. Если его нет в списке, фактически подключённый MCP не предоставляет эту диагностику: проверьте путь запуска в регистрации клиента и активный релиз через `npm run update:status`, даже если другая копия пакета уже обновлена. Одна версия пакета не различает коммиты; сравнивайте также путь и отпечаток кода. Не присылайте полный приватный конфиг или значения ключей.

Если OpenCode не показывает HTTP-заголовки, используйте блок `HTTP diagnostics` в тексте ошибки инструмента. Адаптеры Jira/Zephyr и Confluence добавляют его автоматически после HTTP-ответа с ошибкой; отдельная настройка клиента или перехватывающий прокси не нужны. После обновления пакета перезапустите клиент. Пример сокращённого блока при создании кейса:

```text
HTTP diagnostics: {"request":{"sentAt":"2026-10-19T09:00:00.000Z","method":"POST","url":"https://jira.company.example/rest/atm/1.0/testcase","headers":{"X-Sp-Secret":true,"Authorization":true,"Cookie":false,"Content-Type":"application/json"},"authScheme":"bearer","bodyBytes":420,"redirectsFollowed":0},"response":{"status":403,"headers":{"content-type":"text/plain","x-request-id":"gateway-request-42"},"transactionId":"dd55cf41-1e9c-4f74-8d9e-9c307a5e0a63"}}
```

`X-Sp-Secret: true` означает, что заголовок присутствовал в параметрах запроса непосредственно перед вызовом `fetch`; `false` — отсутствовал. Значения ключа, Authorization и cookies скрыты, тело запроса заменено его размером в байтах, query-параметры URL исключены. При ошибках также маскируются отражённые в ответе значения отправленных учётных данных. Из заголовков ответа выводится только разрешённый набор диагностических полей, включая тип содержимого и идентификаторы запросов; `Set-Cookie` исключён. Блок возвращается через MCP как часть ошибки и не создаёт отдельный файл журнала.

Для ИБ сохраните этот блок, исходный текст ошибки и точное время: по `transactionId` или идентификаторам из `response.headers` можно найти отказ в логах шлюза. Локальное `true` подтверждает подготовку заголовка, но факт получения и принятия ключа проверяется на шлюзе. При редиректах с настроенным ключом блок описывает последний запрос, включая фактический метод и число переходов. Без ключа автоматические редиректы выполняет `fetch`: `request` описывает исходную отправку, а `response.url` и `response.redirected` — конечный ответ. Диагностика относится к уже выполненному вызову и не повторяет создание кейса.

### Проверка совместимости со сторонними Jira/Confluence MCP

Если корпоративная защита требует `X-Sp-Secret`, после настройки Jira/Confluence выполните:

```bash
npm run configure:sp-secret
```

Команда отдельно спросит значение для каждого включённого подключения. Ввод скрыт. Enter сохраняет прежнее значение (или пропускает настройку, если его ещё нет); `-` удаляет заголовок. Значение также можно задать при обычном `npm run configure:jira` / `npm run configure:confluence`. После изменения полностью перезапустите AI-клиент.

Заголовок необязателен и дополняет авторизацию. Он хранится в поле `spSecret` выбранного подключения в приватном конфиге Testdocs Kit, сохраняется при обновлении и не копируется в конфиги AI-клиентов. Jira передаёт его также в Zephyr. При прямом запуске адаптеров доступны `JIRA_SP_SECRET` и `CONFLUENCE_SP_SECRET`; штатный launcher берёт значение из приватного конфига. В блок `headers` локального MCP в OpenCode его добавлять не нужно. Для `--answers` допустимо необязательное строковое поле `spSecret` внутри конкретной записи `connections.jira[]` / `connections.confluence[]`; секреты не следует передавать аргументами командной строки.

В Zephyr заголовок используется для обоих семейств API — `/rest/tests/1.0/*` и `/rest/atm/1.0/*`, включая чтение, внутренний fallback, создание и разрешённые исправления. Отдельно вводить ключ для Zephyr не нужно: он берётся из Jira-подключения, выбранного для TMS, при Basic, PAT и браузерной сессии. Если Jira доступна, а Zephyr возвращает `403`, проверьте, что запускается актуальная версия MCP, клиент перезапущен после настройки, а `spSecret` сохранён именно в выбранном Jira-подключении. Ключ Confluence или другого Jira-подключения автоматически не подставляется. Если в этой конфигурации отказ сохраняется, нужны конкретный метод, URL без секретов и ответ шлюза для проверки прав и маршрута.

При Basic с API-токеном и PAT Jira, Zephyr и Confluence автоматически следуют HTTP-редиректам. С настроенным `X-Sp-Secret` переходы разрешены только в пределах того же origin (схемы, хоста и порта), максимум 20: это не позволяет перенести секрет на другой сервер. Для межсерверного перехода укажите конечный доверенный URL сервиса и задайте секрет для него. При перенастройке адреса прежний X-Sp-Secret автоматически не подставляется. Без X-Sp-Secret действует стандартный `fetch`, снимающий Authorization при смене origin. Браузерная сессия и переиспользование сессии после входа по паролю сохраняют ручную обработку редиректов; их API-запросы и проверка сессии также используют заголовок.

Чтобы временно повторить настройку сторонних MCP с отключённой проверкой сертификатов, после получения этой версии выполните в каталоге Testdocs Kit:

```bash
npm run setup -- --reuse --skip-dependencies --skip-browser-auth --insecure-atlassian-tls
```

Флаг сохраняется для всех включённых Jira/Confluence-подключений с Basic/PAT и действует также на Zephyr через Jira. Обычное обновление сохраняет этот выбор. Можно совместить получение обновления и включение режима: `npm run update -- --insecure-atlassian-tls`. Затем полностью перезапустите AI-клиент и повторите тот же запрос. HTTPS остаётся, но подлинность сертификата сервера временно не проверяется. Токены, браузерные сессии и настройки TLS других интеграций этот флаг не меняет.

Для возврата проверки сертификатов:

```bash
npm run setup -- --reuse --skip-dependencies --skip-browser-auth --verify-atlassian-tls
```

После возврата также перезапустите клиент. Если прямой HTTP 403 сохранился, отключение проверки сертификатов не устранило отказ: сохраните HTTP-статус, Content-Type и диагностические заголовки ответа без токенов/cookies. Для постоянного решения ошибок сертификатов используйте CA-бандл ниже.

### Jira работает, а Zephyr возвращает `404`

Для чтения одного кейса MCP автоматически пробует полный `/rest/atm/1.0` и запасной `/rest/tests/1.0`. Если оба варианта недоступны, уточните у администратора название и версию приложения, права пользователя и доступность этих API-префиксов.

### Ошибка сертификата

Ошибки `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `SELF_SIGNED_CERT_IN_CHAIN` и `UNABLE_TO_GET_ISSUER_CERT` означают, что Node.js не может построить доверенную TLS-цепочку.

Предпочтительное решение — настроить сервер так, чтобы он отдавал полную цепочку сертификатов. Для корпоративного или отсутствующего промежуточного CA можно безопасно передать PEM-бандл:

```bash
npm run setup -- --answers "$HOME/.config/testdocs-kit/config.json" --skip-dependencies --ca-file /absolute/path/to/ca-bundle.pem
```

В каталоге [`certificates/`](../certificates/) находится проверенный публичный промежуточный сертификат GlobalSign, который нужен серверам с сертификатом `GlobalSign GCC R3 DV TLS CA 2020`, но не отправляющим intermediate:

```bash
npm run setup -- --answers "$HOME/.config/testdocs-kit/config.json" --skip-dependencies --ca-file "$PWD/certificates/globalsign-gcc-r3-dv-tls-ca-2020.pem"
```

TLS-проверка при этом остаётся включённой.
