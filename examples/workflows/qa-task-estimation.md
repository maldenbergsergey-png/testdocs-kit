# Проверочные сценарии QA-оценки

Учебные ручные прогоны для [qa-task-estimation](../../skills/qa-task-estimation/SKILL.md). Все описания и часы ниже относятся только к этим входным данным; это не нормативы команды и не результаты реального тестирования продукта. Сценарии проверяют решения и арифметику, а не буквальное совпадение формулировок. Применять [методику](../../rules/qa-task-estimation-rules.md) и [правила команды](../../rules/qa-estimation-team-rules.md).

Общее входное условие сценариев 1-5: пользователь явно просит оценить только Dev; Stage, релизная регрессия и Prod находятся за их границей. Эта граница должна остаться в итоговом комментарии. Сценарии 6-10 проверяют дополненный профиль и матрицы.

## 1. Только бэкенд

Запрос:

> Оцени изменение API редактирования профиля: добавлена валидация необязательного поля, контракт ответов сохранён. UI не меняется и по условиям этой задачи не входит. Нужно проверить валидное, пустое и невалидное значение, права владельца и другого пользователя, сохранение/чтение данных, соседнее редактирование старых полей. По нашей предварительной разбивке: анализ 0,5 ч, подготовка 0,5 ч, API 2 ч, документация 0,5 ч, регрессия 1 ч, один локальный цикл ретеста с оформлением 1 ч. Дополнительный цикл при повторном дефекте потребует 1 ч; это отдельный риск. Создание автотестов и специальные проверки не входят.

Результат прогона:

- Предварительная оценка: B = 5,5, R = 1, T = 6,5 чел.-ч; часы основаны на переданной разбивке, не объявлены нормативом.
- Web, iOS и Android не применимы по границам запроса. Регрессия сохранена: редактирование прежних полей профиля.
- Проверки API и сохранения/чтения учитываются один раз; отдельная строка интеграций не добавляет те же проверки повторно.
- Один плановый цикл ретеста включён в B; R покрывает только второй цикл. Документация включена в часы, кейсы не создаются.

## 2. iOS и Android

Запрос:

> Оцени изменение экрана выбора адреса на обеих платформах. Для учебного расчёта используем по одному физическому устройству каждой платформы; точные модели и ОС ещё уточняем. Сценарии выбора адреса одинаковы. На Android дополнительно изменилось поведение системной кнопки возврата. Активные работы: общий анализ 0,5 ч, подготовка данных 1 ч, общая документация 0,5 ч, независимый API 1 ч, функциональный прогон iOS 2 ч и Android 3 ч, регрессия соседнего сохранения адреса по 0,5 ч на платформу, один ограниченный цикл ретеста и результаты 1 ч на обе платформы суммарно. Дополнительный риск - повторная настройка сборки Android, 1 ч. Ожидание сборки может занять 4 календарных часа.

Результат прогона:

| Работа | Чел.-ч |
| --- | ---: |
| Общий анализ и подготовка | 1,5 |
| Общая документация | 0,5 |
| API | 1 |
| iOS | 2 |
| Android | 3 |
| Регрессия сохранения адреса | 1 |
| Ретест и результаты | 1 |
| B | 10 |
| R: активная повторная настройка Android | 1 |
| T | 11 |

Предварительная оценка сохраняет отдельные прогоны платформ и различие Android. Общие 2 ч не удваиваются, одинаковые клиентские сценарии исполняются на обеих платформах. Модели/ОС не выдуманы; расширение матрицы меняет оценку. Четыре часа ожидания вынесены за трудозатраты, дата завершения не обещается.

## 3. Несколько задач с общей регрессией

Запрос:

> Оцени совместную поставку двух изменений: A меняет фильтрацию списка, B меняет сортировку того же списка. Одна сборка, стенд и набор данных. Уже согласованные уникальные работы A - 3 ч, B - 4 ч, включая их отдельный функциональный прогон и плановый локальный ретест. Общая подготовка 1 ч, обновление общей документации 1 ч и регрессия пагинации/сброса фильтров 2 ч выполняются один раз. Совместное действие нового фильтра и сортировки требует ещё 1 ч. Риск повреждения общего набора данных потребует повторной подготовки на 1 ч.

Результат прогона:

| Вклад в пакет | B | R | T, чел.-ч |
| --- | ---: | ---: | ---: |
| A, уникальные работы | 3 | 0 | 3 |
| B, уникальные работы | 4 | 0 | 4 |
| Общие работы | 4 | 1 | 5 |
| Взаимодействие фильтра и сортировки | 1 | 0 | 1 |
| Пакет | 12 | 1 | 13 |

Часы A/B названы вкладом в пакет, а не самостоятельными полными циклами. Общая регрессия и риск не задвоены. При раздельных поставках требуется пересчёт: прежнее переиспользование не гарантировано. Дополнительная проверка взаимодействия не потеряна ради предполагаемой экономии.

## 4. Неполное описание с возможной предварительной оценкой

Запрос:

> Сколько займёт QA? На существующей web-форме добавляются два необязательных текстовых поля, сохранение уже есть. Новые роли и мобильные клиенты не заявлены. Формат и максимальная длина пока обсуждаются, спецификация по ссылке недоступна. Нужна предварительная оценка с документацией, проверкой сохранения старых полей и одним локальным ретестом. Нормативов нет.

Результат прогона - предварительный экспертный диапазон; часы ниже являются суждением для этого учебного объёма:

| Работа | Простые поля без новых правил | Дополнительные форматы и границы |
| --- | ---: | ---: |
| Анализ, подготовка данных | 0,5 | 1 |
| Ввод/ошибки UI и сохранение/чтение через существующий API | 1 | 2 |
| Документация | 0,5 | 0,5 |
| Регрессия сохранения прежних полей | 0,5 | 1 |
| Один локальный цикл ретеста и результат | 0,5 | 0,5 |
| B, чел.-ч | 3 | 5 |
| R: повторная подготовка данных при несовместимости текущих записей | 0,5 | 1 |
| T, чел.-ч | 3,5 | 6 |

Для предварительного планирования: 3,5-6 чел.-ч с уже включённым резервом; верхний вариант предполагает дополнительные валидации. Риск применим из-за новых сохраняемых полей: резерв покрывает дополнительные данные/диагностику совместимости, а не разработку миграции. Если это влияние отсутствует после уточнения, резерв снимается.

Допущения: одна основная desktop-конфигурация и существующая роль, без новых прав, миграции или интеграции. Это условия оценки, не установленные требования. iOS/Android не заявлены; они находятся за предварительной границей, а не подтверждены как незатронутые. Неизвестные валидации отражены сценариями, не нулём. Существенные уточнения: форматы/лимиты и необходимость проверок других браузеров или прав. Уверенность низкая из-за недоступной спецификации; полный опросник не требуется.

Контроль границы: на запрос "Оцени задачу по недоступной ссылке" без описания поведения числовой итог не выдаётся. Нужны хотя бы изменение, затронутые платформы и ожидаемый результат.

## 5. Новые обязательные правила и сравнение с фактом

Запрос:

> В этой web-задаче прежняя база 5 ч, включая анализ, подготовку, документацию, Chrome, регрессию и один ретест; резерв 1 ч только на восстановление данных, итог 6 ч. Постоянное правило только для текущего проекта: впредь добавляй один выборочный прогон Safari на согласованной конфигурации. На сопоставимых задачах именно такой объём занимал 1 ч активной работы. К iOS и Android правило не относится. Сохрани правило в известном частном файле команды и пересчитай оценку.

Результат прогона:

- Правило получает область проекта, условие обязательности, глубину "выборочный прогон", источник из сообщения и дату уточнения; час - сопоставимая история для этого объёма, не универсальная цена браузера.
- Добавляется отдельный вклад Safari 1 ч. Прежние блоки и риск восстановления данных сохраняются. B: 5 → 6, R: 1 → 1, T: 6 → 7 чел.-ч. Дельта +1 ч объяснена расширением обязательного покрытия.
- В разрешённом частном хранилище сохраняется новая редакция с сохранением остальных правил и проверяется чтением. В ручном прогоне реальное хранилище не изменяется. При недоступной записи агент применяет правило в текущем обсуждении и сообщает, что долговременное сохранение не выполнено.
- Следующая оценка этого проекта использует правило без повторного запроса. Другой проект или iOS/Android не наследуют его автоматически. Предложенный пользователем разовый дополнительный прогон не становится постоянным правилом.

Продолжение:

> Факт: прежние базовые работы 5 ч, Safari 1,5 ч, восстановление данных 0,5 ч. Ожидали доступ ещё 3 ч.

Результат сравнения: активный факт 7 ч против плана 7 ч; базовые работы 6,5 против 6 (+0,5 на Safari), реализованный риск 0,5 против резерва 1. Три часа ожидания отдельно. Равенство итогов не скрывает отклонение базы. Один пример не меняет постоянный норматив автоматически.

Дополнительная проверка правила расчёта: если команда отдельно задаёт резерв 10% от базы без ретеста, вычислить процент ровно от указанной базы и проверить пересечение с прежним резервом. Если база процента не определена и существенно влияет на итог, уточнить её либо показать варианты; не добавлять процент поверх тех же рисков молча.

## 6. Подзадачи, коллега на Stage и общий smoke

Вход: головная история меняет способ выбора адреса. Подзадача A - API, B - web-клиент этого API. Полные описания обеих частей и контракт доступны в приложенном контексте. Пользователь просит отдельные комментарии и итог пакета. Согласованные часы: уникальные Dev-работы A - 3, B - 4; общие исследование и документация - 2. На Stage другой QA тратит 0,5 на погружение/данные и 1,5 на кросс-проверку обеих частей. Общий Prod smoke - 1. Плановые ретесты входят в указанные работы; отдельный риск повторной совместной проверки при несовместимом контракте - 1,5.

Результат прогона: B = 3 + 4 + 2 + 0,5 + 1,5 + 1 = 12, R = 1,5, T = 13,5 чел.-ч. Комментарии A и B явно названы вкладом в пакет; общие 5 ч базы и 1,5 ч резерва раскрыты отдельно. Изучение A для оценки B не добавляет второй полный API-прогон. Кросс-проверка не пропала и не превратилась в умножение Dev на число QA. Prod smoke учитывается один раз. Никакой комментарий не публикуется.

Контроль неполноты: если описание A или контракт недоступны, результат не заявляет их прочитанными. Возможная предварительная оценка B содержит условие о стабильном контракте; существенное неизвестное не получает нулевые часы.

## 7. Браузеры, реальные устройства и макетные ширины

Вход: web-задача, согласованы макеты 390 и 1366 px, tablet-макета нет. Safari поддерживается. Есть Mac и реальный iPhone; Android доступен через ферму. Дополнительно заказчик просит Firefox и 768 px, которых нет в основной матрице этой задачи. Применяется переданный профиль.

Результат прогона:

- Основная матрица использует реальные 390 и 1366 px, несмотря на то, что в PDF они приведены среди примеров сверхмакетных ширин. Классификация зависит от текущего макета, а не самого числа.
- Учитываются Chrome, Яндекс.Браузер, Safari macOS; контрольные mobile web сценарии на Safari iOS и Chrome Android через ферму, Яндекс.Браузер на выбранном доступном мобильном устройстве.
- На мобильных браузерах не повторяется весь desktop-пул. Подготовка фермы видна, второй полный прогон той же конфигурации не создаётся.
- Firefox и 768 px оцениваются отдельно как запрос дополнительного покрытия. Если выбраны в итог, это работа базы, не резерв за неизвестное. Ширины 375/768/1440 не добавляются автоматически из PDF.
- Нет основания для проверки нативного приложения или отдельного физического планшета.

Вариация: в макетах отдельно согласован 1920 px, но неизвестно, входил ли он в оценку разработки. Проверка не исчезает: её объём показывается отдельной строкой с уточнением границы, без процента от разработки и повторной надбавки за те же сценарии.

## 8. Мобильные приложения и smoke до стора

Вход: подзадачи iOS и Android используют общий готовый API. Изменяются экран адреса и геолокация. Есть по одному реальному устройству обеих платформ; фактический Android находится внутри диапазона 13-16, поддерживаемая iOS соответствует проекту. Дополнительно запрошен foldable. Есть сборки с Prod-бэкендом до публикации в сторах.

Результат прогона: общие независимые API-проверки имеют одно место учёта, клиентская связка и геолокация проверяются отдельно на iOS/Android. Две платформы не превращаются в одну строку или механическое удвоение времени. Android 13-16 не означает четыре прогона. Foldable оценивается дополнительно. Ферма/эмулятор не объявляются безусловной заменой аппаратной геолокации. Smoke на Prod-сборке до стора выделен по этапу и не подтверждает публикацию.

Вариация Android-only: в оценку не добавляется iOS только из-за наличия двух строк в матрице.

## 9. ИИ, ретесты, ожидание и исторический процент

Вход: разработка оценена в 20 ч, приложенная старая таблица предлагает 25-30%. Для выбранного узкого QA-объёма известны активные работы: подготовка контекста ИИ 0,5 ч, проверка результата человеком 1 ч, исправления 0,5 ч, оставшийся ручной прогон 1 ч. Один плановый ретест - 1 ч. Агент выполняет свои действия 2 часа без участия человека. Плохая аналитика и частичная самопроверка разработчиком могут привести к одному дополнительному циклу на 1 ч. Ожидание восстановления среды DevOps - 4 часа. Пользователь задаёт рабочий человеко-день 6 часов.

Результат: B = 4, R = 1, T = 5 чел.-ч, то есть 5/6 человеко-дня при указанном коэффициенте. Два часа машинной работы и четыре часа ожидания отдельно; они не прибавляются к активным часам. Один риск-цикл не посчитан дважды под аналитикой и самопроверкой. Значение 5 ч получилось из работ, а не выбором 25% от 20. Календарная дата не выводится из количества QA или человеко-дней.

Вариация без нормы рабочего дня: человеко-часы сохраняются, для дней требуется основание пересчёта; скрытого деления на 8 нет. Без фактических данных об ИИ не появляется стандартная скидка. Плановая валидация не добавляется повторно как риск.

## 10. Минимально полезный выпуск и отложенные кейсы

Вход: заказчик определил минимально полезный результат как совместную поставку API и web-формы; API отдельно ценности пользователю не даёт. Третья часть улучшает оформление и может быть отложена. Техническая поставка API без включения UI допустима по подтверждённой конфигурации. Запрошено сравнение вариантов, создание задач не запрошено.

Результат прогона: различаются полный состав, API+форма как минимально полезная фича и скрытая техническая поставка API. Во всех вариантах раскрыты свои зависимости, подготовка, нужные прогоны и риски; минимальный состав не называется минимальной регрессией. Для скрытой поставки включены проверка предусмотренной недоступности и влияние на текущее поведение; способ скрытия не выдуман. Проверка связки при последующем включении не потеряна.

Если при крайнем дефиците времени команда допускает перенос кейсов небольшой фичи, их часы видны как отложенная работа. Чек-лист и финальная валидация сохраняются. Будущая задача, архивирование кейсов и изменение доступности фичи не выполняются автоматически.
