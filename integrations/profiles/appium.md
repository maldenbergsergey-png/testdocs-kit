# Appium MCP для подготовленных мобильных устройств

Использовать после выбора транспорта по [мобильным правилам](../../rules/execution-native-rules.md). QA-план, разрешения и доказательства определяют [правила выполнения](../../rules/task-execution-rules.md). Подготовка сборок и WDA вынесена в [памятку проекта](../../docs/mobile-testing.md).

## Подключение в Testdocs Kit

Используется проект [appium/appium-mcp](https://github.com/appium/appium-mcp). MCP запускается установленной командой `appium-mcp` по stdio; Appium HTTP server, XCUITest driver, WDA и приложение проверяются отдельно. На macOS Appium пригоден для Android, iOS Simulator и физических iPhone. Windows-маршрут XCUITest имеет ограниченную поддержку, требует физического iPhone с iOS 18+ и подготовленного WDA; Simulator на Windows отсутствует. Точные ограничения проверять для установленных версий по [Non-macOS Hosts](https://appium.github.io/appium-xcuitest-driver/latest/guides/non-macos-hosts/).

`setup`/`update` используют `appium.mode: "auto"`: подключают найденный `appium-mcp` как `testdocs_appium`, при отсутствии сохраняют auto и продолжают остальные интеграции. Уже сохранённый off не включается. SDK, драйверы и npm-пакет автоматически не устанавливаются. Сначала установить совместимый Node.js и CLI по официальной инструкции, например `npm install --global appium-mcp`; для повторяемой среды проект фиксирует выбранную версию пакета. Из установленной копии Kit:

```bash
npm run configure:appium -- --appium-mode auto
npm run check:appium
```

`on` требует CLI; `off` отключает launcher. Нестандартный путь:

```text
npm run configure:appium -- --appium-mode on --appium-command /absolute/path/to/appium-mcp
npm run configure:appium -- --appium-mode off
```

На Windows передавать абсолютный путь к `appium-mcp.cmd`, при пробелах заключать путь в кавычки. Поиск использует абсолютные каталоги PATH, стандартный npm-каталог Windows и Homebrew-каталоги Mac. Явный путь не заменяется другим CLI. В закрытом config.json сохраняются только command/resolvedCommand, mode/enabled и необязательные javaHome/androidHome; endpoint, UDID и capabilities относятся к проекту/задаче, не к общей установке. SDK-пути подхватываются из JAVA_HOME и ANDROID_HOME/ANDROID_SDK_ROOT; весь environment и секреты не копируются.

Launcher работает из data directory вне checkout. Снимки попадают в `appium/captures/` этого каталога; нужные файлы переносить в `evidence/` workspace задачи. `NO_UI=true` возвращает текст и пути к файлам; файлы доступны агенту на том же компьютере. Дополнительный AI vision выключен, API-ключ модели для обычного управления не нужен. Codex получает runtime-tools и таймауты 60/180 секунд; инструменты установки SDK/подготовки WDA не входят в его allowlist. Другие клиенты применяют свои разрешения; общие границы подготовки остаются в мобильных правилах.

`check:appium` вызывает только `--help`. У CLI нет документированного `--version`: неизвестный аргумент может запустить MCP вместо завершения. Успех диагностики подтверждает запуск CLI, не MCP-handshake, WDA, доступность телефона или тест приложения. `--no-cli` пропускает запуск даже этой диагностики.

## Передача и выбор Appium-сессии

1. Проверить реальные tools и схемы текущего подключения. Обычные имена: `appium_session_management`, `appium_get_page_source`, `appium_screenshot`, `appium_find_element`, `appium_gesture`, `appium_set_value`. Не подставлять старую схему по памяти.
2. Если переданы URL Appium-сервера и sessionId, использовать `appium_session_management` с `action=attach` и этим `remoteServerUrl`. `action=list` показывает сессии, известные данному MCP, а не все внешние устройства/серверы. Не вызывать локальный `select_device` ради уже выделенной внешней сессии.
3. Если открыто приложение, но Appium-сессия ещё не создана, получить из контекста endpoint подготовленного сервера, UDID, platformVersion и bundle/package ID. Создать сессию на этом сервере через `remoteServerUrl` и явные capabilities. На Windows использовать этот серверный режим, не встроенный macOS-only мастер подготовки. Не требовать готовый sessionId, если доступных данных достаточно для создания сессии.
4. Для установленного приложения не передавать `appium:app` с файлом сборки. Использовать bundleId/appPackage и `appium:noReset=true`; для уже открытого iOS-приложения также `appium:autoLaunch=false`. На Windows с подготовленным WDA передать `appium:usePreinstalledWDA=true` и его bundle ID либо предоставленный `appium:webDriverAgentUrl`. Не выбирать стартовые capabilities, которые переустанавливают/сбрасывают приложение или автоматически обходят проверяемые разрешения. Для задачи установки/холодного запуска применять её явно согласованные условия.
5. Сопоставить сессию и устройство по фактам, сохранить sessionId и передавать его в адресных вызовах. Прочитать дерево/экран и проверить исходное состояние по мобильным правилам. Создание или attach сессии само по себе не подтверждает готовность приложения.
6. Использовать наблюдаемые accessibility ID/текст и небольшие группы действий. После смены экрана перечитать дерево; element UUID от другой сессии не переносить. Сохранять настоящий файл снимка и привязку к проверке/устройству. Если путь снимка принадлежит другому хосту, получить файл разрешённым каналом, не объявлять недоступный путь сохранённым доказательством.
7. Чужую attached-сессию не удалять; `detach` отключает MCP от неё без удаления на сервере. Не вызывать terminate/reset/clear для завершения обычного осмотра. Любая смена устройства или пересоздание сессии должны сохранять согласованный scope и состояние приложения.

При сбое назвать подтверждённую ступень: CLI, MCP-handshake, Appium server/session, соединение с устройством, подпись/запуск WDA или приложение/вход. Запросить только недостающее; продолжить независимые проверки другой платформы. Облако и загрузку сборок не использовать как автоматическую замену локального подключения.
