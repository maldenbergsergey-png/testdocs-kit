# Maestro MCP для локального мобильного тестирования

Официальный MCP входит в Maestro CLI и запускается командой `maestro mcp`. Он управляет приложением через интерфейс устройства. QA-правила, выбор устройства, границы действий и доказательства определяет [task-execution-rules.md](../../rules/task-execution-rules.md).

## Подготовка компьютера

- Общая часть: Maestro CLI и Java 17+ с рабочим `JAVA_HOME`. Установка и обновление CLI выполняются отдельно по [официальной инструкции](https://docs.maestro.dev/maestro-cli/how-to-install-maestro-cli). Установщик Testdocs Kit не скачивает SDK или эмуляторы.
- Android: Android Studio/Android SDK, Platform Tools (`adb`), созданный и запущенный AVD, установленная тестовая APK и её package ID. Перед запуском должны быть известны тестовый backend и подходящая учётная запись. Сам по себе установленный Android Studio не означает наличие устройства и приложения.
- iOS на Mac: Xcode, Command Line Tools, runtime iOS Simulator и запущенный симулятор. Нужна сборка `.app` для Simulator и её bundle ID. Обычная IPA для iPhone/App Store не заменяет сборку для симулятора. Доступность физического iPhone не выводить из успешного прогона в Simulator. См. [iOS в Maestro](https://docs.maestro.dev/get-started/supported-platform/ios).

Это подготовка для управления приложением через MCP. Если подходящей среды нет, применяется раздел "Проверка по материалам пользователя" в [правилах выполнения](../../rules/task-execution-rules.md): анализ скринкастов и скриншотов остаётся доступным без установки мобильных инструментов.

## Подключение в Testdocs Kit

При `setup` и `update` по умолчанию используется `maestro.mode: "auto"`: установленный CLI подключается как `testdocs_maestro`, без CLI сохраняется режим auto, остальные интеграции продолжают работать. После поздней установки CLI нужно повторно применить настройки и перезапустить клиент. Сохранённый `off` не включается при обновлении.

Из установленной копии kit:

```bash
npm run configure:maestro -- --maestro-mode auto
npm run check:maestro
```

`on` требует наличия CLI и останавливает настройку с понятной ошибкой, если он не найден; `off` отключает подключение. Путь можно задать явно:

```text
npm run configure:maestro -- --maestro-mode on --maestro-command /absolute/path/to/maestro
npm run configure:maestro -- --maestro-mode off
```

Поиск использует абсолютные каталоги PATH, `~/.maestro/bin` и стандартные Homebrew-каталоги на Mac. Явный путь не заменяется другим найденным CLI. Launcher сохраняет отдельные stdout/stderr и запускает официальный CLI без дополнительного MCP-сервера. Его рабочий каталог - data directory kit вне репозитория; пути к flows и доказательствам передавать абсолютными, внутри workspace текущей задачи.

В приватном `config.json` можно указать `maestro.javaHome` и `maestro.androidHome` абсолютными путями. При настройке сохраняются только эти SDK-пути из `JAVA_HOME` и `ANDROID_HOME`/`ANDROID_SDK_ROOT`, если они заданы, чтобы запуск из GUI не зависел от терминальной сессии. Секреты и весь PATH в клиентскую конфигурацию не копируются. Учётные данные приложения остаются вне flows и отчётов.

Установщик регистрирует подключение в выбранных Codex, OpenCode, Claude Code и generic-конфигурациях. Codex получает список локальных tools и таймауты запуска/операции 60/180 секунд. В остальных клиентах применяются их текущие разрешения. Cloud-прогон не входит в этот профиль и требует отдельного запроса. Для Claude Code установщик сохраняет существующую регистрацию; после `off` launcher запрещает её запуск, при необходимости пользователь может удалить оставшуюся запись средствами клиента.

`check:maestro` проверяет только запуск CLI и наличие подкоманды MCP. Он не запускает приложение и не объявляет MCP-handshake или тест устройства успешными. Проверка установщика с `--no-cli` пропускает даже запуск CLI и явно сообщает об этом.

## Preflight в задаче

1. Проверить реальные tools текущего подключения. В новых версиях используются `list_devices`, `inspect_screen`, `take_screenshot`, `run`, `cheat_sheet`; старые версии могут выдавать `inspect_view_hierarchy`, `tap_on`, `input_text`, `launch_app`, `run_flow` и `run_flow_files`. Параметры брать из текущей схемы, а не из этого списка.
2. Выполнить выбор устройства и передачу приложения по [правилам выполнения](../../rules/task-execution-rules.md). Диагностика подключённых устройств: Android - `adb devices -l`, iOS - `xcrun simctl list devices booted`. При пустом списке проверить также выключенные устройства через Android Studio/Xcode.
3. Получить экран и дерево переданного приложения. Для тестирования сначала показать scoped checklist; для источника матрицы или кейсов следовать [Live product context](../../rules/integration-rules.md#live-product-context).
4. Выполнять небольшие группы действий с проверкой наблюдаемого результата. Для неизвестного синтаксиса сначала прочитать schema/`cheat_sheet`. Переданный flow проверить до запуска. Не добавлять `launchApp` как обязательный первый шаг для уже открытого приложения. Если запуск нужен по сценарию, учитывать его настройки: автоматическая выдача разрешений может пропустить проверяемый диалог.
5. Сохранить изображения из MCP в `evidence/` задачи. Для inline-изображения использовать сохранение байтов либо штатный захват выбранного устройства. Проверить файл и связать со строкой отчёта или источником запрошенного артефакта.

Пример запроса после подготовки окружения:

```text
Протестируй восстановление пароля в Android-приложении на запущенном эмуляторе.
Нужная тестовая сборка и app ID: <переданные значения>.
Сборку я уже установил, приложение открыто на <выбранное устройство>.
Требования: <описание или ссылка на задачу>.
Покажи отчёт со скриншотами.
```

Актуальные команды и настройка клиентов: [официальный Maestro MCP](https://docs.maestro.dev/get-started/maestro-mcp). Наличие команды или зелёный статус подключения не заменяет фактическую проверку поведения приложения.
