# Update Postman collection

Read [the common contract](../../rules/core.md) once per task and [collection maintenance rules](../../rules/postman-collection-rules.md). Keep project bindings and task artifacts outside the portable pack under [project conventions](../../rules/project-conventions.md).

## Inputs and collection discovery

Accept a local/attached YAML or JSON contract, a repository file URL, a branch/MR/commit URL, or a task-specific export. No GitLab connection or issue key is required. A supplied file is a first-class source; do not require a repository URL as well. A file can describe a whole API or only the changed methods.

Use [collect-test-context](../collect-test-context/SKILL.md) only for external task anchors needing retrieval. For repository reads, load the [GitLab profile](../../integrations/profiles/gitlab.md) when applicable. For live collection reads/writes, load the [Postman profile](../../integrations/profiles/postman.md). Inspect actual capabilities; do not assume a tool name or cloud access to local Native Git assets.

Resolve saved repository bindings using the [repository profile](../../integrations/profiles/git-repositories.md) when configured. Read the actual local checkout (v3 YAML or v2.1 JSON), a supplied export/file, or Postman MCP for an explicitly cloud-backed target. Do not substitute cloud state for unsynced Git files. Resolve a previously supplied private binding before asking for identifiers. Without a baseline, analyze the supplied contract and request only the collection/export needed for an exact patch. Do not reconstruct unseen requests or validator code. Without a contract, identify the specific missing method/response definition.

## Workflow

1. Establish input provenance, target collection, affected API/service/version and maintenance intent. Select the contract revision under the shared rules; separate it from the execution environment. Record unknown file provenance honestly.
2. Read the current request tree and inherited collection/folder scripts, authentication, variables and shared validator. Locate affected requests by service/version, HTTP method and normalized path, with operationId as supporting evidence. Include every relevant scenario variant; distinguish complete discovery from a partial listing. For placement, data/auth prerequisites or restricted endpoints, read [workflow rules](../../rules/postman-workflow-rules.md); map producers/consumers, variable scopes, extraction scripts, cleanup and effective run order before editing.
3. Compare the task change, chosen operation definitions and current requests. Resolve referenced schemas at the same revision and expand only affected dependencies. Inventory request parameters/body separately from response status/media schemas. A method already in the collection still requires this comparison.
4. Prepare the smallest necessary patch against the current collection. For a new method, select a suitable existing folder and insert it after its data/auth producers and before consumers or cleanup as needed. Reuse the established authentication flow or externally supplied token/cookie binding. Include restricted methods with execution prerequisites. Implement the documented assertions completely for supported response shapes; expose unsupported or ambiguous parts instead of claiming complete automation. Justify every necessary change to an existing item's name, folder or relative order; do not reorganize the collection for convenience.
5. Validate the collection format and changed script syntax, source-to-schema coverage, allowed fields, preserved request/folder IDs and unrelated content. Check dependency order and the intended run selection, credential bindings, variable writes/reads and missing-prerequisite handling under the workflow rules. Exercise the affected validator with representative positive and negative local fixtures when it is available. Do not send live requests merely to generate tests. A requested live run additionally follows [execution permissions](../../rules/execution-access-rules.md) and [execution rules](../../rules/task-execution-rules.md).
6. Show a reviewable diff or save the requested local collection/patch in the task workspace. Git publication additionally follows the [repository profile](../../integrations/profiles/git-repositories.md#agent-git-workflow): push opt-in and task publication intent are separate from local saving. For external publication, apply [write rules](../../rules/external-write-rules.md) and the collection preflight, conflict and retry boundaries in the shared maintenance rules. A clear request to apply/save changes to the specified Postman collection needs no repeated confirmation after the payload is ready and permissions are satisfied.
7. Read back successful writes and compare the affected content and preserved structure. Report the exact affected methods/folders, justified structural changes, contract revision, actual validation/run scope and remaining gaps. Include prerequisite order/auth bindings without secret values and restricted methods when relevant. Distinguish prepared, saved, applied and executed. If the comparison produces no change, return that result without rewriting the collection.

For connection or future automation advice, use the [setup guide](../../integrations/postman-collection-sync.md). Do not install connections or create a schedule as a side effect of using this skill.
