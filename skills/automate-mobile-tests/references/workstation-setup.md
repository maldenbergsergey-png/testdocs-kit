# Настройка рабочего места тестировщика

Применять, когда пользователь просит настроить мобильные автотесты на его компьютере. Использовать доступ к локальным инструментам в рамках запроса и [терминальных правил](../../../rules/terminal-access-rules.md). Для инструкции без действий использовать [памятку команды](../../../docs/mobile-autotests.md).

1. Определить ОС, оболочку, выбранный AI-клиент, рабочую папку, точный Git-репозиторий и цели запуска. Прочитать README, конфиг, зависимые инструменты и пробный тест из проекта. В уже скачанном репозитории проверить `git status`, ветку и `origin`. Использовать подходящий checkout. Если в нём есть незакоммиченная работа, сохранить её состояние и при необходимости подготовить отдельную папку. Уточнить только сведения, которые нельзя получить из доступного контекста.
2. Проверить версии Git, SDK, runner и runtime, от которых зависит выбранный проект. Клонировать проект, если его ещё нет. Установить недостающее из согласованного или официального источника. Установить зависимости по lock-файлу, если он есть. Применить точечную настройку только выбранных подключений в [Testdocs Kit](../../../docs/installation.md#полная-и-точечная-перенастройка), сохранив действующие MCP и настройки других проектов. Проверить появление инструментов в AI-клиенте после перезапуска, если он нужен. Успешная команда диагностики CLI подтверждает только запуск CLI.
3. Для Android проверить SDK, ADB и статус выбранного устройства, для iOS Simulator проверить Xcode Runtime и запущенный симулятор. Для физического iPhone применить [подготовку Appium и WebDriverAgent](../../../docs/mobile-testing.md#wda-для-физического-iphone), проверить адрес сервера, выбранный UDID и доступ к приложению через сессию. Использовать предусмотренный проектом runner для сохранённого YAML. Проверить точную сборку и стенд. Если одна цель недоступна, продолжить с готовыми целями и указать причину отдельно.
4. Восстановить доступ через штатный пользовательский вход, доверие телефону или приватный ввод токена. Попросить пользователя выполнить нужный интерактивный шаг только в момент, когда он требуется. При сбое отдельно проверить источник токена, его формат, адрес сервиса и целостность после сохранения по [инструкции токена](../../../integrations/profiles/mobile-test-runners.md#настройка-токена-allure). Избегать повторного запроса настроенных доступов. Держать значения секретов вне чата, исходников, истории команд и отчётов.
5. Проверить список сценариев и выполнить один сохранённый smoke в разрешённой тестовой среде. Для прогона настройки выбрать сценарий без изменения аккаунта и других записей, если такие изменения не входят в поручение. Проверить, что свежий результат содержит выполненный сценарий и соответствует коду выхода. При запросе публикации использовать подтверждённый проектный Allure и проверить ссылку. Иначе проверить доступный локальный отчёт. Настройка компьютера и публикация подчиняются разным разрешениям.
6. Вернуть точную папку, команды для обычного запуска и запуска одного кейса, результат по каждому устройству и ссылку или путь к отчёту. Если часть настройки зависит от пользователя или его администратора, назвать конкретное действие и что уже проверено. Подтверждать готовность на основании прогона сохранённого теста, а работу публикации - по открытому отчёту целевого проекта.
