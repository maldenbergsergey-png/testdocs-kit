# Agent guidance

This repository is a portable skill pack for QA test documentation, not an application.

- Treat `rules/` as the source of truth. Read every rule file referenced by the active skill; do not duplicate or override policy inside a skill.
- Route by user intent; never require the user to know a skill name or negate unwanted artifacts. “How should I test this?” routes to `explain-task-testing` and returns practical guidance without an artifact. “Test/verify this implementation” routes to `execute-task-testing` and produces an evidence-backed execution report. When the user names a concrete artifact, return only that artifact; reserve the checklist-plus-cases package for an explicit request for all test documentation or a full package. Do not silently expand an ambiguous “prepare testing” request to every artifact. Checklist-only, full package, cases-only, task-scoped non-regression cases, and targeted-scope requests route through `prepare-task-testing`. Bug-report drafting or Jira bug creation uses `create-bug-report`. Release Test Run/Test Cycle preparation or creation uses `create-release-test-run`. Generate-only uses `generate-test-cases`; optimization/refactoring or review of supplied cases uses `review-test-cases`; a specific-case apply/update uses `update-test-cases`; coverage-only uses `analyze-test-coverage`; matrix uses `build-coverage-matrix`; regression organization uses `build-regression-model`; corpus/rule derivation uses `derive-test-case-standard`. A Jira/GitLab issue, merge request, release version, Confluence page, Figma node, standalone document, file, or chat requirement can each be the scope source. Direct skill calls remain supported.
- Keep task checklists distinct from permanent Test Cases. A checklist captures task-specific verification; permanent cases require durable regression value.
- Work only from context available to the user, whether supplied in chat, local files, or an available integration.
- Never invent missing requirements, system behavior, identifiers, test data, or existing coverage. State material gaps explicitly.
- Prefer minimum sufficient detail: every case must be executable by a tester unfamiliar with the project, while UI cases must not be overloaded with internal implementation detail.
- Follow the shared output language and punctuation rules in `rules/README.md`: use natural tester prose, short hyphens and double quotation marks, preserve literal technical/source content, and omit unnecessary agent/process narration.
- Model one base case for an identical shared block, delta-only cases for supported product-direction differences, and at most one coherent administration case per creation, update, or deletion operation. Put the creation/configuration dependency first, allow an explicit skip when a conforming entity already exists, and never rely on hidden case order. Read `rules/project-conventions.md` for cross-company isolation and use direction names only from the current project's supplied context.
- Keep permanent web UI cases on the primary desktop breakpoint; do not create resolution or breakpoint variants. Group small related elements by block and split only oversized blocks into meaningful functional parts.
- Keep `Цель` concise, create named clickable material links, and keep the required concise TMS change comment outside the case body.
- Treat MCP and external systems as optional. If a needed integration is unavailable, ask for the relevant context manually and continue when it is supplied.
- When an issue key or external link is supplied, anchor retrieval to it and use `collect-test-context`; without a key or link, do not search an arbitrary company system.
- Treat previous tester checklists found in Jira comments as traceable practitioner evidence, not as the sole source of truth or existing permanent TMS coverage. Validate reused checks against current requirements and mark their comment provenance in generated checklist rows.
- Treat Jira, Confluence, and TMS access as independent capabilities. Never claim that existing cases were checked when only Jira issues were readable.
- Show results in chat by default.
- Select skills progressively: use their discovery descriptions first, read only the skills needed for the current intent, and add another skill when a newly discovered need actually requires it. Do not preload the entire skill pack.
- Store task execution reports and evidence outside the repository in the user data directory, separated by project and task. Read a saved task workspace only when the current request needs it. Skill-pack updates must not delete or overwrite this data.
- Follow `rules/task-execution-rules.md` for evidence capture and reuse: save screenshots during UI checks, including successful results, maintain their checklist-row mapping, and use saved files for later attachment requests instead of repeating completed checks.
- For bug reports, read the exact project's Jira create metadata before a create operation. Use dedicated semantic fields when present and fall back to a structured Description without duplication. Require `FE. `, `BE. `, `Android. `, or `iOS. ` in bug titles. Include supplied bug evidence uploads and small Description previews under `rules/bug-report-standard.md`. Keep reporter/author and assignee on the authenticated tester by default; use the same user for an unambiguous specialist field. Do not guess optional labels, components, ownership, priority, or other routing.
- Treat every change to existing documentation as a proposal for human review. Review output includes a complete corrected proposal when findings affect content.
- Use an external write operation only after an explicit user request or confirmation. Existing-case updates must re-read and pass the connector's stale-proposal check. Never automatically perform destructive changes or delete external test cases; use `RETIRE_PROPOSAL` for reviewable retirement recommendations.
- Test Run creation and its linked Jira QA work-item creation require an explicit create request, complete preflight, and connector support for every named relation and assignment. A partial failure must preserve and report successful object IDs; never delete or duplicate external objects automatically to recover.
- Publishing a finalized checklist to a Jira comment or sending it to QA Report are separate optional writes. Perform either only when the user explicitly asks for that destination. A QA Report editor URL may be opened only as a separate external browser tab/window, never embedded.
- For QA Report delivery, including a supplied temporary API prompt, read `integrations/profiles/qa-report.md` and the delivery rules in `rules/integration-rules.md` before assessing capability. The documented temporary session can use an available HTTP/terminal client without a dedicated MCP; handle the supplied runtime token under that profile and verify its saved receipt. Carry the known task URL and testing stand into the report, distinguish the empty starter template from existing content, and verify the dedicated fields as well as text and files.
- Keep edits focused on rules, skills, examples, agent guidance, integrations, MCP adapters, and their portable installer or verification scripts. Do not add an application, service, database, model dependency, or orchestration runtime.
- Keep the development checkout separate from deployed skill-pack copies. Developing or testing a change does not authorize updating deployed client configuration, retargeting installed skill links, or modifying another installation; use isolated installer fixtures until the user explicitly requests deployment.
- Keep credentials outside the repository and client configuration. Installer output must not print secrets, and external write tools must remain disabled by default.
