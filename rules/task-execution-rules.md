# Правила исследования и выполнения тестирования задачи

**Статус:** переносимый baseline, требующий человеческого review.

## Маршрутизация по намерению

- Запрос «как протестировать», «расскажи, что проверить», «помоги разобраться с проверкой» без просьбы создать артефакт запускает объяснение подхода. Результат — понятное руководство в чате, без Jira Wiki checklist и постоянных Test Cases.
- Запрос «протестируй», «проверь реализацию», «выполни тестирование» запускает выполнение проверок. Агент собирает контекст, готовит рабочий checklist, выполняет доступные действия и формирует отчёт с фактическими результатами.
- Запрос конкретного артефакта сохраняет существующую маршрутизацию: checklist, Test Cases, bug report, coverage analysis или Test Run не подменяются выполнением тестирования.
- Постоянные Test Cases не входят в выполнение задачи автоматически. Их подготовка требует отдельного явного запроса, в том числе после завершения проверки.

## Объяснение подхода

1. Выделить проверяемое изменение, подтверждённые требования, зависимости и неизвестные факты.
2. Объяснить тестировщику обычным языком: какое состояние подготовить, какое действие выполнить, что наблюдать и с каким источником сравнить.
3. Раскрыть незнакомые термины или механизмы настолько, чтобы специалист, знакомый с проектом, мог выполнить проверку без догадок.
4. Разделить основной сценарий, ошибки и границы, влияние на соседнюю функциональность и необходимые диагностические наблюдения.
5. Не оформлять ответ как checklist или Test Cases, если пользователь их не просил.

## Выполнение тестирования

### 1. Подготовка

- Получить только релевантный контекст из явно переданной задачи, требований, комментариев, макетов, контрактов, MR/commit/diff, файлов и доступных интеграций.
- Установить фактический scope текущей итерации. Исключённые или ещё не реализованные части не считать дефектами.
- Определить окружение, сборку, роли, данные, доступы, поверхности и критерии завершения. Не переносить значения между компаниями и проектами.
- Подготовить пустой checklist по `test-checklist-standard.md` и показать его до начала систематического прогона. В QA Report пустой план не отправлять.
- Согласование плана не даёт разрешения на внешние записи. Оно подтверждает только scope и способ выполнения проверок.

### Проверка браузерных возможностей

- До вывода «нет браузера» проверить доступные инструменты текущего клиента, включая поиск отложенных MCP tools. В OpenCode локальный Playwright MCP пакета называется `testdocs_browser`; ориентироваться на фактические имена выданных инструментов.
- Для UI/SPA использовать браузерную навигацию и snapshot, затем действия по наблюдаемым элементам. Webfetch не заменяет взаимодействие с UI; его transport error не доказывает недоступность стенда, отсутствие браузера или проблему VPN.
- Читать схему фактически доступного инструмента: параметры и набор tools зависят от установленной версии. Если snapshot возвращён ссылкой на локальный файл, прочитать этот файл доступным файловым инструментом и использовать наблюдаемые в нём элементы для следующего действия. Относительные пути `testdocs_browser` разрешать от корня установленного kit (рабочего каталога MCP), а не от произвольного проекта клиента.
- Различать отсутствие MCP, ошибку запуска MCP/Chrome, отсутствие авторизации и сетевую ошибку браузера. Указывать наблюдаемую причину. Если tools недоступны, проверить статус MCP клиента; если доступна только ручная настройка, дать команду `npm run configure:browser` из установленного kit и попросить перезапустить клиент. Не устанавливать интеграцию без запроса пользователя.
- Локальный браузер использует сеть компьютера, на котором запущен MCP. Это не означает автоматическое использование cookies личного браузера. Режим `persistent` открывает отдельный Chrome с сохраняемым профилем; `extension` подключается к выбранной пользователем вкладке Chrome/Edge через официальное расширение. Не копировать cookies и не подменять профиль личным каталогом браузера.
- При запросе авторизации открыть целевой ресурс и использовать доступную штатную сессию. Если требуется пароль, одноразовый код, SSO или подтверждение расширения, запросить только необходимое действие пользователя в браузере и после его завершения продолжить проверки. Не отправлять пользователя выполнять весь прогон из-за одного шага входа.
- Профиль авторизации не является доказательством теста. Промежуточные файлы Playwright находятся во временном каталоге вне репозитория; нужные обезличенные доказательства перенести в workspace конкретного проекта/задачи. Не запускать одновременно два прогона с одним persistent-профилем; при конфликте не удалять профиль.

### 2. Исполнение

- По возможности выполнять проверки самостоятельно доступными инструментами пользователя. Разрешено читать страницы, вызывать API, анализировать ответы, макеты, логи и предоставленные медиа в пределах задачи.
- Если для продолжения нужен вход, попросить пользователя открыть ресурс или пройти штатную авторизацию в браузере. Не запрашивать пароль, cookie, токен или секрет в чате.
- Если действие недоступно агенту, дать пользователю один конкретный набор действий и указать, какие наблюдения, скриншоты, видео, ответ API или идентификаторы нужны для продолжения.
- Анализ присланного видео или скриншота отмечать как проверку по предоставленному материалу. Не выдавать его за самостоятельное взаимодействие с системой.
- Не считать проверку успешной только из-за отсутствия видимой ошибки. Сопоставлять результат с конкретным требованием, контрактом, макетом или подтверждённым ожидаемым поведением.
- Остановить повторение одного и того же безрезультатного действия. После разумной попытки зафиксировать ограничение и перейти к независимым проверкам.

### 3. Поверхности

- **Backend/API:** выполнять безопасные запросы, сохранять метод, endpoint, обезличенные параметры, статус, релевантную часть ответа и correlation/request ID; сравнивать с контрактом и требованиями. Изменяющие запросы выполнять только в тестовом окружении и в пределах явного запроса на тестирование.
- **Интеграция:** установить входное событие, канал доставки, ожидаемое преобразование, результат на стороне получателя, повтор, таймаут и обработку ошибки — только когда эти свойства подтверждены источниками.
- **Web frontend:** проверять функциональность, состояния, вёрстку и соответствие конкретному Figma-узлу или другому макету. Фиксировать браузер, версию и viewport для визуальных проблем.
- **Адаптив и браузеры:** использовать матрицу, заданную проектом или пользователем. При отсутствии такой матрицы предложить Chrome, Яндекс Браузер и Safari, а также размеры из макетов и существенные промежуточные размеры; это предложение не становится выполненным покрытием. Firefox и Opera добавлять по запросу или подтверждённому риску.
- **Mobile:** при доступе взаимодействовать с приложением на доступном устройстве или симуляторе. Иначе запросить запись, начинающуюся с исходного состояния и показывающую действия и результат; сохранить ограничения наблюдения.
- **Logs/observability:** искать по точному окружению, временному интервалу, service/correlation ID и минимально необходимому набору индексов. Маскировать секреты и персональные данные.

## Статусы отчёта

Использовать только следующие execution-статусы:

| Статус | Когда применять | Jira Wiki Markup |
| --- | --- | --- |
| `OK` | Весь пункт выполнен, результат полностью совпал с подтверждённым ожидаемым | `{color:#14892c}*OK*{color}` |
| `НЕ OK` | Наблюдается подтверждённое несоответствие | `{color:#d04437}*НЕ OK*{color}` |
| `ПОЧТИ OK` | Основной результат достигнут, но есть локальное подтверждённое отклонение, не позволяющее поставить `OK` | `{color:#6554c0}*ПОЧТИ OK*{color}` |
| `НЕ ПРОВЕРЕНО` | Проверка не выполнялась или отсутствует доступ/сборка/данные | `{color:#6b778c}*НЕ ПРОВЕРЕНО*{color}` |
| `ЧАСТИЧНО ПРОВЕРЕНО` | Выполнена только явно указанная часть пункта или матрицы | `{color:#bf6700}*ЧАСТИЧНО ПРОВЕРЕНО*{color}` |
| `ТРЕБУЕТ УТОЧНЕНИЯ` | Нет однозначного ожидаемого результата или источники конфликтуют | `{color:#0052cc}*ТРЕБУЕТ УТОЧНЕНИЯ*{color}` |

`ПОЧТИ OK` требует описания конкретного отклонения. `ЧАСТИЧНО ПРОВЕРЕНО` требует перечисления выполненной и оставшейся части. `НЕ ПРОВЕРЕНО` требует причины. Статус не заменяет фактический результат.

## Отчёт

- По умолчанию вернуть Jira Wiki отчёт в чате. Если пользователь запросил HTML-отчёт, оформить результат в HTML по правилам ниже; выбор формата не является разрешением на публикацию во внешней системе.
- Сохранить структуру и семь колонок исходного checklist. Заполнить `Фактический результат`, при необходимости `Комментарий`, и `Статус`.
- В фактическом результате указать только наблюдаемое. Ссылаться на доказательства по понятному имени или относительному пути внутри task workspace.
- Для `НЕ OK` и `ПОЧТИ OK` указать ожидаемый источник, фактическое отклонение, окружение и доказательство. Не создавать Jira Bug автоматически; отдельный запрос маршрутизируется в `create-bug-report`.
- В конце кратко указать scope прогона, окружение/сборку, покрытые платформы и браузеры, ограничения, найденные несоответствия и оставшиеся вопросы.
- Публиковать финальный результат в Jira или QA Report только по явному запросу пользователя и через соответствующий разрешённый инструмент.

### Понятное и подтверждённое описание несоответствий

- Для каждого несоответствия описать одну сопоставимую пару: что должно происходить по конкретному требованию и что наблюдалось при тех же условиях. Назвать экран или элемент, действие или состояние и точное отличие простым языком. Читатель должен определить проблему по ячейкам `Ожидаемый результат` и `Фактический результат`, без догадок и поиска объяснения в комментариях. Формулировки «не соответствует требованиям», «сломана вёрстка» или «работает неправильно» без конкретного отличия недостаточны.
- В `Ожидаемый результат` включить понятный критерий и подтверждение: короткий точный фрагмент реального требования с именованной кликабельной ссылкой на конкретный пункт, раздел, комментарий или узел макета. Если прямой якорь недоступен, дать ссылку на документ и точное название раздела/номер пункта для поиска. Не придумывать цитаты, ссылки, номера пунктов, ограничения или ожидаемое поведение. Не выдавать собственный пересказ за дословную цитату.
- Текст требования с точной ссылкой достаточен для текстового основания: скриншот требования необязателен. Если он полезнее, приложить читаемый снимок релевантного фрагмента с той же ссылкой и подписью после текста ожидаемого результата. Это не отменяет правила включения изображения макета при запрошенном визуальном сравнении в HTML.
- В `Фактический результат` описать наблюдаемое поведение и явно назвать расхождение с указанным критерием. Для видимого UI-несоответствия приложить после полного текста скриншот, на котором видно именно это расхождение, с подписью о подтверждаемом факте. Общий снимок страницы, не показывающий проблему, не считается её подтверждением. Если различие проявляется только в переходе или во времени, дополнить снимки последовательностью состояний или видео; для API/данных использовать релевантный ответ, лог или другое непосредственное доказательство, а не имитировать визуальное подтверждение.
- Если скриншот недоступен или не фиксирует заявленный факт, явно указать пробел и доступное доказательство; не утверждать, что несоответствие подтверждено скриншотом. Отделять наблюдаемый результат от предположений о причине. Недостаток доказательств учитывать при выборе статуса по правилам выше.
- Если ожидаемое поведение не найдено в доступных требованиях, неоднозначно или противоречит другому актуальному источнику, описать наблюдение и вынести ожидаемое правило в `ТРЕБУЕТ УТОЧНЕНИЯ`; не объявлять дефектом отличие от предположения агента. Предыдущий checklist сам по себе не заменяет подтверждённое требование.
- Перед выдачей для каждого `НЕ OK` и `ПОЧТИ OK` проверить цепочку: конкретный источник → подтверждённый ожидаемый результат → наблюдаемое отличие → доказательство этого отличия. Удалить неподтверждённые утверждения или явно обозначить их как вопросы, не скрывая реально наблюдавшиеся факты.

### Текст и изображения в ячейках

- В ячейке `Фактический результат` сначала разместить весь текст наблюдения законченными предложениями или абзацами, затем отдельный блок доказательств с изображениями и короткими подписями. Изображения остаются в той же ячейке, но не вставляются внутрь слова, предложения, абзаца или между частями описания. После начала блока изображений допускаются только подписи и ссылки, а не продолжение основного текста результата.
- Несколько скриншотов расположить после текста в порядке описанных состояний; подписать, какое состояние или наблюдение подтверждает каждый. При необходимости сослаться на номера скриншотов из текста. Не вставлять дубли ради количества.
- В HTML использовать отдельные блочные элементы для текста и каждого изображения, например `<p>` и `<figure>` с `<figcaption>`. Изображения выводить с `display: block; max-width: 100%; height: auto`, без обтекания текста и абсолютного позиционирования. Подпись и `alt` должны отличать источник и состояние. Размер миниатюры не должен растягивать колонку; дать возможность открыть читаемый оригинал.
- При вставке через редактор сначала полностью заполнить текст ячейки, затем создать отдельный блок в её конце и вставить изображения туда. Не полагаться на сохранённую позицию курсора или символьные смещения после предыдущих вставок.
- Для Jira Wiki сохранять правила синтаксиса таблицы: не добавлять физические многострочные ячейки или сырой HTML. Представление доказательств выбирать по возможностям назначения, сохраняя порядок «полный текст → доказательства». Не считать, что Jira-import автоматически поддерживает HTML и вложения.
- В переносимом HTML изображения должны открываться у получателя: использовать включённые в документ данные изображений, поставляемую вместе с HTML папку с относительными путями либо поддержанные назначением вложения/URL. Пути к временному файлу или `file://` на компьютере автора не являются доставленным изображением. Не загружать доказательства во внешний сервис без запроса на этот способ доставки.
- Перед выдачей открыть готовый HTML, а после разрешённой вставки в редактор осмотреть результат там, если доступен просмотр. Проверить целостность текста, положение и загрузку изображений, подписи, сохранность колонок и читаемость оригиналов. Если визуальная проверка недоступна, явно отметить это ограничение; не объявлять вёрстку отчёта проверенной по одному исходному HTML.

Порядок внутри ячейки (схема, не готовые данные отчёта):

```text
Фактический результат:
  Полный текст всех наблюдений и отклонений.
  Факт — скриншот 1: <состояние экрана>.
  Факт — скриншот 2: <другое подтверждаемое состояние>.
```

## Доказательства

- Сохранять материал только когда он подтверждает результат или нужен для воспроизведения. Не собирать снимки каждого успешного шага без причины.
- Именовать файл `<номер-пункта>-<actual|expected|log|request|video>-<номер>.<ext>`, например `12-actual-01.png`.
- Для изображения макета сохранять прямую именованную ссылку на Figma-узел или другой переданный источник. Если пользователь просит использовать макеты при визуальном тестировании и получить HTML-отчёт, получить реальный снимок/экспорт соответствующего макета и включить его изображением в отчёт вместе со скриншотом реализации; одной ссылки на Figma недостаточно. В остальных случаях локальный снимок expected добавлять, когда ссылка недоступна, состояние может измениться или сравнение иначе неоднозначно.
- Для такой визуальной проверки разместить изображение `Макет — <экран/состояние>` после текста в ячейке `Ожидаемый результат`, а `Факт — <экран/состояние>` — после текста в ячейке `Фактический результат` той же строки. Не выдавать снимок реализации за макет. Сопоставлять один и тот же блок, состояние и поддержанный размер экрана; не растягивать изображения с искажением пропорций. Существенное различие исходных размеров или состояний указать как ограничение сравнения.
- Получать снимок макета доступным экспортом, инструментом изображения или захватом реально открытого макета, а не генерировать или реконструировать ожидаемый вид. Если получить изображение невозможно, сохранить доступную ссылку и явно указать отсутствие снимка; запросить экспорт или доступ только когда это блокирует сравнение. Не заявлять полноценную визуальную проверку без достаточного материала.
- Обрезать доказательство до релевантной области, сохраняя достаточно контекста для идентификации экрана, запроса или временного интервала.
- Никогда не сохранять Authorization headers, cookies, пароли, токены, приватные ключи или лишние персональные/production-данные.

## Локальная история

- Создавать task workspace только когда тестирование порождает материалы, должно продолжиться позже или пользователь просит сохранить контекст.
- Хранить его вне репозитория в пользовательском data directory. Использовать структуру `projects/<project>/tasks/<task>/` и не смешивать проекты с похожими ключами.
- Читать только workspace указанной задачи или явно нужные проектные настройки. Не индексировать и не загружать всю историю в контекст по умолчанию.
- Хранить отчёты в `reports/`, доказательства в `evidence/`, вложения источников в `attachments/`, обезличенные запросы/ответы в `requests/`.
- Обновление skill pack не должно изменять пользовательский data directory.
