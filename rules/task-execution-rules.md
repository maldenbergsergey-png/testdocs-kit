# Task execution

Read [report rules](execution-report-rules.md) for every execution report and [evidence rules](execution-evidence-rules.md) before capturing or reusing evidence. Read only the applicable surface: [web](execution-web-rules.md), [native](execution-native-rules.md), or [supplied media](execution-media-rules.md). Native control also uses the [Maestro profile](../integrations/profiles/maestro.md).

## Выполнение тестирования

### 1. Подготовка

- Получить только релевантный контекст из явно переданной задачи, требований, комментариев, макетов, контрактов, MR/commit/diff, файлов и доступных интеграций.
- Установить фактический scope текущей итерации. Исключённые части не добавлять в checklist и результаты; не считать их дефектами. Блокировку выбранной проверки отражать по правилам отчёта.
- Определить окружение, сборку, роли, данные, доступы и критерии завершения из текущего контекста. Выбрать поверхность по платформе задачи, затем проверить её доступность; не спрашивать платформу повторно, если выбор однозначен. Не переносить значения между проектами.
- До проверочных действий подготовить пустой checklist по `test-checklist-standard.md`, включая быстрый запрос: достаточно минимального числа строк. По умолчанию показать его в чате и не отправлять пустой план в QA Report. При явно выбранной [прямой записи через API](checklist-delivery-rules.md#direct-api-delivery) создать план в назначении и кратко назвать scope в чате. Осмотр исходного экрана для подготовки допустим. Продолжить без отдельного согласования плана, если scope, критерии и доступ ясны; ожидать только недостающие сведения или действия пользователя.

| Поверхность | Среда для взаимодействия |
| --- | --- |
| Web, включая mobile web | Браузер; согласованные размеры и платформы |
| Нативное iOS | iOS Simulator на macOS (Xcode) |
| Нативное Android | Android Emulator/AVD из Android Studio/Android SDK |

Таблица задаёт обычный локальный маршрут, а не обязательную матрицу всех платформ. Явно выбранное поддерживаемое устройство или инструмент сохранять; симулятор/эмулятор не обозначать как физическое устройство.

### 2. Исполнение

- По возможности выполнять проверки самостоятельно доступными инструментами пользователя. Разрешено читать страницы, вызывать API, анализировать ответы, макеты, логи и предоставленные медиа в пределах задачи.
- Если для продолжения нужен вход, попросить пользователя открыть ресурс или пройти штатную авторизацию в браузере. Не запрашивать пароль, cookie, токен или секрет в чате.
- Если действие недоступно агенту, дать пользователю один конкретный набор действий и указать, какие наблюдения, скриншоты, видео, ответ API или идентификаторы нужны для продолжения.
- Анализ присланного видео или скриншота отмечать как проверку по предоставленному материалу. Не выдавать его за самостоятельное взаимодействие с системой.
- Не считать проверку успешной только из-за отсутствия видимой ошибки. Сопоставлять результат с конкретным требованием, контрактом, макетом или подтверждённым ожидаемым поведением.
- Сохранять доказательство сразу при наблюдении результата, до перехода к следующему состоянию или очистки данных, по [правилам доказательств](execution-evidence-rules.md). Запрос прикрепить материалы позднее должен использовать файлы этого прогона, а не запускать уже выполненные проверки заново.
- Остановить повторение одного и того же безрезультатного действия. После разумной попытки зафиксировать ограничение и перейти к независимым проверкам.

### Исправление чек-листа во время тестирования

- Использовать чек-лист для организации прогона. Проверять продукт по актуальным требованиям, макетам нужного состояния и подтверждённым решениям по задаче. Формулировка «расхождение с чек-листом» не является основанием для дефекта продукта. Называть конкретный источник и отличие от него; ошибку самого плана обозначать отдельно как «Ошибка в чек-листе».
- Если реализация отличается от записанного ожидания, сначала повторно прочитать его источник и проверить применимость: экран, роль, состояние, версия и границы задачи. Затем различить дефект продукта, ошибку чек-листа и недостаток/противоречие требований. Совпадение реализации с требованием при неверной строке чек-листа — ошибка плана, а не дефект продукта. Если и реализация, и строка неверны, зафиксировать обе проблемы отдельно.
- Исправлять содержание проверки только по конкретному подтверждению: пункту требования, соответствующему узлу макета или явному решению с указанием источника. Наблюдаемая реализация, текущий статус прогона, догадка агента или желание получить `OK` не обосновывают изменение ожидаемого результата. Отсутствие описания кнопки в чек-листе или упоминания в тексте не доказывает, что она запрещена на экране; для сравнения с макетом проверить, что он относится именно к этому экрану и состоянию.
- Предложение исправления должно содержать номер строки, прежнюю формулировку, причину ошибки, точный фрагмент/изображение источника с именованной ссылкой и полную исправленную строку. Сохранять наблюдаемый фактический результат и доказательства. Обозначать изменение как предложение для человеческого review; не выдавать его за исходный согласованный план и не вносить его незаметно. Для добавления, исключения или разделения проверок также показывать основание и влияние на объём прогона, не теряя исходные номера и результаты.
- Фактический результат менять только при обнаруженной ошибке записи или новом наблюдении, а не из-за правки ожидания. Указывать, что исправлено и на каком доказательстве основано; новый прогон отличать от предыдущего. Не редактировать скриншоты и цитаты так, чтобы скрыть расхождение.
- После подтверждённого исправления критерия заново оценить имеющееся доказательство. Если оно полностью покрывает исправленную проверку, объяснить пересмотр статуса без выдуманного повторного прогона; иначе выполнить недостающую проверку или поставить соответствующий статус неполного прогона. Не переносить `OK` автоматически и не стирать историю ошибочной оценки.
- Если источник недоступен, не определяет правило или противоречит другому актуальному источнику, сохранить наблюдение и указать `ТРЕБУЕТ УТОЧНЕНИЯ`. Не выбирать ожидаемое поведение по тому, как сейчас работает приложение. Продолжить независимые проверки.
- Изменение опубликованного чек-листа требует явного запроса. Запрос вести результаты текущего прогона через API уже разрешает их запись по [правилам доставки](checklist-delivery-rules.md#direct-api-delivery); он не разрешает незаметно менять критерии или перезаписывать чужой план. Предложение исправления само по себе не разрешает запись.

### 3. Поверхности

- **Backend/API:** выполнять безопасные запросы, сохранять метод, endpoint, обезличенные параметры, статус, релевантную часть ответа и correlation/request ID; сравнивать с контрактом и требованиями. Изменяющие запросы выполнять только в тестовом окружении и в пределах явного запроса на тестирование.
- **Интеграция:** установить входное событие, канал доставки, ожидаемое преобразование, результат на стороне получателя, повтор, таймаут и обработку ошибки — только когда эти свойства подтверждены источниками.
- **Web frontend:** проверять функциональность, состояния, вёрстку и соответствие конкретному Figma-узлу или другому макету. Фиксировать браузер, версию и viewport для визуальных проблем.
- **Адаптив и браузеры:** использовать матрицу, заданную проектом или пользователем. При отсутствии такой матрицы предложить Chrome, Яндекс Браузер и Safari, а также размеры из макетов и существенные промежуточные размеры; это предложение не становится выполненным покрытием. Firefox и Opera добавлять по запросу или подтверждённому риску.
- **Mobile:** следовать [мобильному маршруту](execution-native-rules.md) и [профилю Maestro](../integrations/profiles/maestro.md).
- **Logs/observability:** искать по точному окружению, временному интервалу, service/correlation ID и минимально необходимому набору индексов. Маскировать секреты и персональные данные.
