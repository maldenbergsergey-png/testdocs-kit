# Правила маршрутизации пользовательских QA-сценариев

**Статус:** действующий переносимый baseline; проектные placeholders требуют явных данных.

Workflow выбирается по пользовательскому intent, а не по знанию имён skills или типу переданного источника. Пользователь может указать Jira key/URL, Confluence URL, отдельный документ, несколько тест-кейсов, локальный файл или требования прямо в чате.

"Протестируй задачу" и "быстро проверь фильтры на указанном экране" направлять в `execute-task-testing` по `task-execution-rules.md`. Просьба использовать открытое web/Android/iOS-приложение как источник матрицы или кейсов сохраняет запрошенный артефакт по `integration-rules.md`, раздел "Live product context".

## Выбор скилла

Имена ниже обозначают внутренний выбор; пользователь их знать не обязан. Конкретный результат выбирается раньше общего слова "тестирование". Если внешнего контекста ещё нет или он устарел, добавляется `collect-test-context` для его чтения; артефакт не меняется. Полный актуальный текст с исходной ссылкой можно использовать напрямую по `core.md`.

| Намерение | Скилл | Результат |
| --- | --- | --- |

| Чек-лист, формальный план проверок | `generate-test-checklist` | Только checklist |
| Новые кейсы, кейсы по задаче или конкретному блоку | `generate-test-cases` | Только кейсы и обязательная подготовка |

## Ветви workflow

- **QA_ESTIMATION:** запрос просит оценить трудозатраты QA, часы для планирования, дополнительную регрессию/ретест, сравнить варианты минимального полезного выпуска, пересчитать оценку или сравнить её с фактом. Используйте `qa-task-estimation` и `qa-task-estimation-rules.md`; результат - краткая оценка каждой задачи для комментария с границами, этапами, человеко-часами и рисками. Учёт будущей документации и выполнения проверок не является поручением создать эти материалы, выполнить тестирование или записать часы в трекер.
- **CHECKLIST_ONLY:** запрос явно просит чек-лист по задаче, документу или переданным требованиям. Соберите только релевантный контекст и сформируйте Jira Wiki checklist. Не запускайте полный TMS-анализ; читайте отдельные cases только когда они нужны для понимания требования или очевидного regression impact.
- **FULL_PACKAGE:** запрос явно просит всю тестовую документацию или полный пакет. Соберите контекст, создайте task checklist, выполните targeted discovery постоянного покрытия, классифицируйте scenarios и подготовьте полные CREATE/UPDATE proposals. Не расширяйте неоднозначное «подготовь тестирование» до полного пакета молча: определите требуемый артефакт из остальной формулировки, а если это невозможно — кратко уточните результат.
- **CASES_ONLY:** запрос явно просит написать тест-кейсы. Создайте только кейсы в указанном scope. Не требуйте от пользователя дополнительно уточнять, что checklist не нужен. Не выполняйте полный coverage report и не утверждайте включение в регрессионную модель, если пользователь этого не просил.
- **TASK_SCOPED_CASES:** запрос явно просит кейсы только для проверки конкретной задачи или прямо исключает их из регрессионной модели. Допускайте стабильные и разовые task-specific сценарии, поддержанные источником. Покажите кейсы отдельно от постоянного покрытия и не создавайте regression links, suite membership или retire/update decisions без отдельного запроса.
- **OPTIMIZE_EXISTING:** запрос просит оптимизировать, отрефакторить, объединить или привести несколько существующих кейсов к текущему стандарту. Проведите review всего supplied-набора, выявите дубли и неверные границы, затем покажите целевую структуру и полные исправленные proposals. Ничего не записывайте и не удаляйте автоматически.
- **REVIEW_ONLY:** запрос явно просит ревью. Проверьте указанные кейсы по действующим правилам и покажите исправленные proposals только при подтверждённых замечаниях.

Модификатор **TARGETED_SCOPE** применяется к любой ветви, когда пользователь просит только определённый блок, сценарий, тип кейсов или часть задачи. Не расширяйте результат до полного пакета и не добавляйте соседние кейсы, кроме явных зависимостей, без которых запрошенный результат неисполним.

## Маршрутизация по источнику

- Jira key или task URL — основной scope anchor; соберите саму задачу и только релевантные связи.
- Confluence URL или отдельный документ — самостоятельный источник требований; Jira-задача не обязательна.
- Документ плюс запрос «сопоставить/связать с существующими кейсами» — выполните targeted coverage analysis по указанному функциональному scope; отсутствие TMS capability не выдавайте за отсутствие кейсов.
- Несколько существующих кейсов — используйте их как baseline для review или optimization; не реконструируйте отсутствующее содержимое по названиям.
- Контекст в чате — достаточный ручной источник, если он определяет исполнимые действия и ожидаемые результаты.

Task checklist содержит всё, что важно проверить в текущем изменении, включая one-time rollout/migration/temporary checks. В `FULL_PACKAGE` постоянный Test Case создаётся только для стабильного, повторяемого, наблюдаемого и диагностически самостоятельного сценария с долгосрочной regression value. В `CASES_ONLY` регрессионная принадлежность остаётся неопределённой без отдельного запроса. В `TASK_SCOPED_CASES` кейсы намеренно остаются вне постоянной регрессионной модели.

Для каждого сценария внутренне определите: нужен ли он для задачи, имеет ли постоянную ценность, найдено ли существующее покрытие и соответствует ли оно новому поведению. Для постоянного покрытия используйте `CREATE`, `UPDATE`, `NO_CHANGE`, `RETIRE_PROPOSAL`, `INSUFFICIENT_CONTEXT`; пользователю показывайте «Создать», «Актуализировать», «Без изменений», «Сделать неактуальным», «Требует уточнения».

## Полный пользовательский результат

Для `FULL_PACKAGE` по умолчанию отвечайте по-русски и показывайте:

1. `Кратко о задаче` — 1–3 предложения и только реально прочитанные источники.
2. `Чек-лист тестирования` — готовый Jira Wiki Markup в fenced `text` block; его разделы выбираются по смыслу и масштабу конкретной задачи, а не из фиксированного набора.
3. `Создать Test Cases — N` — каждый case целиком по `test-case-standard.md`, либо явное отсутствие необходимости.
4. `Актуализировать Test Cases — N` — причина, focused diff `ДОБАВИТЬ/ИЗМЕНИТЬ/УДАЛИТЬ/ОСТАВИТЬ` и полная предлагаемая версия.
5. `Сделать неактуальными — N` — key/URL/name, исчезнувшее или заменённое поведение, причина и предложение сменить организационный статус после review; никогда не удалять.
6. `Без изменений` — все реально проанализированные релевантные cases и причина достаточности.
7. `Ограничения и вопросы` — conflicts, partial/unavailable discovery и недостающие правила.

Показывайте только содержательные разделы. Если изменений постоянного покрытия нет, достаточно одной короткой строки вместо трёх пустых разделов. Не показывайте пользователю названия внутренних skills, raw bundle, служебную классификацию, промежуточные вызовы или успешно восстановленные ошибки интеграций.

При частичном контексте выдайте безопасную часть и вынесите неопределённое в вопросы. Частичный TMS search не доказывает отсутствие coverage и не позволяет категоричный `CREATE`.

Для остальных ветвей возвращайте только запрошенный артефакт, обязательные зависимости и материальные ограничения. Не добавляйте checklist к `CASES_ONLY`, coverage report к `CHECKLIST_ONLY`, полный пакет к `TARGETED_SCOPE` или обучающее объяснение workflow без прямого запроса.
