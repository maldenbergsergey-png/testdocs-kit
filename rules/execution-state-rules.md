# UI-проверки по состояниям экрана

Применять при выполнении web/mobile UI-проверок. При запросе функционального и нефункционального тестирования включать сверку с применимыми макетами и базовую визуальную оценку по [правилам макетов](execution-design-rules.md), без отдельного напоминания. Явные ограничения пользователя сохранять. Другие нефункциональные проверки выбирать по требованиям и scope; осмотр экрана не заменяет проверку производительности, безопасности или доступности.

## Один проход по состоянию

- При подготовке сопоставить строки checklist с экранами и состояниями: например, открытая модалка, ошибка валидации, раскрытый список, загрузка или результат операции. Для каждого состояния определить доступный источник ожидания и зависимые проверки. Это порядок выполнения, а не новый артефакт: сохранять номера и отдельные результаты самостоятельных проверок, не склеивать функциональность и оформление в одну строку ради сокращения маршрута.
- Достигнув нужного состояния, выполнить относящиеся к нему функциональные проверки и сразу доступные визуальные и другие нефункциональные проверки в scope. Сопоставлять именно это состояние с прочитанным макетом; общий вид страницы не подтверждает оформление модалки или ошибки. Не откладывать всю визуальную часть до завершения функционального маршрута.
- До действия, которое уничтожит состояние (закрытие, отправка, переход, смена роли/данных), осмотреть и сохранить ещё нужный вид. Затем проверить результат действия в новом состоянии. Для кратковременных состояний заранее выбрать последовательность снимков или видео; итоговый кадр не подтверждает загрузку, переход или исчезнувшее сообщение.
- Перед уходом сохранить доказательства и привязку по [правилам доказательств](execution-evidence-rules.md). Один читаемый файл использовать для всех действительно показанных критериев; для отличающихся состояний и невидимых частей нужны свои материалы. Не снимать каждое нажатие или все сочетания ролей и размеров вне scope.
- Недоступный макет запросить сразу, сохранить достигнутое состояние для отложенной сверки и продолжить независимые проверки. Явное требование пользователя ждать макеты сохраняет приоритет. Отсутствие источника не превращает базовую визуальную оценку в подтверждённое соответствие макету.

## Сохранение для отложенной сверки

В существующем `reports/evidence-index.md` связать строки с экраном/состоянием, файлами и существенными условиями сопоставления: сборка/окружение, роль/данные, платформа и размер, когда они влияют на критерий. Общие условия записывать один раз. Для отложенной сверки отметить, что уже проверено, что осталось сравнить и какой источник ожидается. Не вводить отдельный реестр или новые колонки отчёта.

Сохранять читаемую область будущего сравнения с ориентирами. Если проверяется расположение блоков экрана, одного кропа кнопки недостаточно; для длинной страницы нужны относящиеся к scope читаемые участки. Сохранённый вид подтверждает только показанное состояние. Сам захват без оценки критерия не является выполненной визуальной проверкой и не получает `OK`.

## Возврат к макетам или расширение проверки

- При получении макета или просьбе дополнительно сверить дизайн сначала прочитать сохранённый отчёт, индекс и нужные изображения этой задачи. Проверить применимость источника и сопоставимость условий. Если индекса нет, восстановить привязку по существующим файлам и их подтверждённому происхождению, не угадывая состояние.
- Сначала сравнить пригодные сохранённые материалы. Выполненные функциональные сценарии заново не запускать. В индексе различать время исходного наблюдения и поздней оценки; не выдавать сравнение старого снимка за новый живой прогон. Новые критерии/строки добавлять явно по [правилам изменения checklist](task-execution-rules.md#исправление-чек-листа-во-время-тестирования), сохраняя исходные результаты.
- Возвращаться в приложение только за конкретным недостающим наблюдением: нужный участок/состояние не снят, файл непригоден, условия несопоставимы, критерий требует взаимодействия или запрошена новая сборка/повторный прогон. Указать пробел и повторить минимально необходимый путь, сохранив новые доказательства отдельно. Изменение сборки не обесценивает факт старого прогона, но старый снимок не подтверждает новую сборку.
- Статусы выбирать по [правилам отчёта](execution-report-rules.md) для каждого критерия. Ожидающая макета сверка остаётся открытой; завершённая функциональная строка сохраняет свой результат.
