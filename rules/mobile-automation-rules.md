# Мобильные автотесты для регресса

## От проверки задачи до автотеста

Для первичной проверки задачи достаточно требований и рабочего чек-листа. QA фиксирует результат на каждой платформе, дефекты и открытые вопросы по [правилам выполнения](task-execution-rules.md). Постоянное покрытие выбирают по повторяемости, наблюдаемому ожиданию и ценности для регресса. Разовая проверка миграции или ещё не согласованное поведение могут остаться в чек-листе.

Автотест можно подготовить по готовому регрессионному кейсу, подтверждённому пункту чек-листа или требованию с однозначным результатом. Сохранять привязку к существующему ключу/ссылке либо к конкретному пункту и требованию. Когда появится кейс, добавить его ключ к тому же flow по соглашению проекта. Для отбора постоянных кейсов применять [правила покрытия](coverage-rules.md) и [правила регрессионной модели](regression-model-rules.md). Для записи в TMS или изменения Test Run требуется соответствующее поручение.

## Содержание и хранение

- Следовать структуре репозитория приложения или выделенного репозитория мобильного QA. Для нового набора подходит `.maestro/`. В общем kit хранятся процедуры и инструменты. Сборки, приватные настройки устройств, тестовые учётные данные и отчёты прогона остаются вне исходников тестов.
- Условия и ожидания брать из требований/кейса. Для элементов использовать подтверждённые идентификаторы доступности или однозначные подписи. Состояние текущей сборки само по себе не устанавливает правильный результат. При неоднозначном селекторе или ожидании обозначить конкретный пробел в черновике.
- Подготовить исходные данные для повторного запуска, ждать наблюдаемого состояния и проверять пользовательский результат. Для сохранения данных проверить повторное открытие, если это предусмотрено требованием. Тест на двух устройствах может использовать общий YAML при совместимых элементах и поведении. Вынести реальные различия в узкие платформенные шаги. Параллельные изменения требуют независимых тестовых данных.
- Перед записью сверить целевой репозиторий, рабочую ветку, актуальный flow и чужие изменения. Публикация коммита, PR/MR и запуск внешнего CI выполняются в рамках поручения и предоставленных прав этого проекта. Использовать уже данное разрешение. При конфликте сохранить работу и сверить актуальную версию. Для записи в TMS действуют [общие правила](external-write-rules.md).

## Результат

Указать, какой файл или набор, какую сборку и на каком устройстве действительно запустили. Для независимых платформ указать отдельные результаты. При расхождении сохранить шаг, ожидание, факт и доступный скриншот/лог по [правилам доказательств](execution-evidence-rules.md). Различать нарушение требования, ошибку теста и недоступность инфраструктуры по наблюдениям. Пустая выборка, только пропуски, синтаксическая проверка, интерактивное нажатие и просмотр скринкаста не подтверждают прохождение сохранённого файла. При недоступном устройстве, сборке или runner сообщить, что уже подготовлено и что ещё предстоит проверить.
