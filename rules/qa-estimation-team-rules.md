# Правила команды и история QA-оценок

**Редакция:** 2026-09-11. Механизм уточнения методики. По поручению пользователя опубликованы [профиль процесса](qa-estimation-profile.md) и [матрица платформ](qa-estimation-platform-matrix.md); нормативов времени пока нет.

## Область действия и применение

При получении инструкции различай постоянное правило команды, условие проекта/платформы, исключение для задачи и предварительное допущение. Не превращай пример в универсальную норму. Используй уже полученные правила в следующих оценках соответствующего scope, не запрашивая весь набор заново.

Постоянная запись должна содержать:

| Поле | Содержание |
| --- | --- |
| Правило и тип | Содержание; постоянное, проектное/платформенное, исключение задачи или допущение. |
| Область действия | Подтверждённые команда, компания/экземпляр системы, проект, платформа или точная задача. Для ручного контекста достаточно однозначной области пользователя, Jira не обязательна. |
| Применимость | Условия обязательности и исключения. |
| Покрытие | Сценарии, глубина, матрица ОС/устройств/браузеров, полный и выборочный прогон, если определены. |
| Расчёт и формат | Норматив или способ расчёта с единицами и базой; блоки и формат результата, если заданы. |
| Происхождение | Источник, известная дата уточнения, статус подтверждения и какое прежнее правило заменяет. |

Сохраняй только переданное; отсутствие необязательного поля не блокирует применение понятного правила. Если новое правило явно заменяет старое в той же области, применяй новую редакцию с источником. Если источники противоречат друг другу без ясного приоритета, обозначь конфликт и влияние на оценку; не выбирай правило только по свежести сообщения. Используй сценарии, если они позволяют продолжить.

Подтверждённые инструкции пользователя могут дополнять или менять состав блоков, глубину, матрицы, нормативы, формулы и формат стартовой методики. Укажи используемую редакцию и расчёт. При процентном правиле должна быть понятна база; если её выбор существенно меняет часы и она не задана, уточни её либо покажи условные варианты. Не добавляй процент поверх тех же уже учтённых работ.

## Хранение и повторное использование

Следуй изоляции из [project-conventions.md](project-conventions.md). История, оценки и частные проектные соглашения хранятся вне переносимого репозитория и клиентской конфигурации. По прямому поручению пользователя в пакет можно включить переносимый профиль процесса и матрицу, как в текущей редакции. Это не разрешает публиковать внутренние домены, идентификаторы проектов, имена людей, доступы или сырые частные заметки. Не добавляй такие данные в общий `SKILL.md`, примеры или installer defaults.

Используй известное пользователю частное хранилище или пользовательский data directory Testdocs Kit, вычисляемый существующей функцией `getDataDir()` из [scripts/paths.mjs](../scripts/paths.mjs). При наличии Node.js его можно получить из корня доступной копии пакета:

```bash
node --input-type=module -e 'import { getDataDir } from "./scripts/paths.mjs"; console.log(getDataDir())'
```

Внутри него для оценок используй:

```text
qa-estimation/<scope-id>/team-rules.md
qa-estimation/<scope-id>/estimates/<task-or-package-id>/<revision>.md
```

Это обычные Markdown-файлы, не новая служба или база данных. `scope-id` и имена файлов - безопасные локальные имена без разделителей пути, `..` и секретов. Запиши внутри подтверждённую область, чтобы совпадение коротких имён не смешало проекты/компании. Не ищи правила в произвольных чужих проектах. В новой сессии прочитай известный файл только после проверки его области; при неоднозначной принадлежности сначала уточни её.

Если пользователь поручил применять постоянное правило впредь и доступна разрешённая запись, обнови соответствующий частный файл, сохранив остальные правила и историю замены, затем перечитай его. Такое поручение включает сохранение в известном частном хранилище; дополнительное подтверждение для той же записи не нужно. Изменение существующего содержания показывай пользователю как полное затронутое предложение для review с указанием сохранённого пути. Для иных случаев достаточно применения в текущем контексте.

Не создавай личное хранилище при разработке или тестировании навыка и не обновляй другие установки. Если путь неизвестен, механизм отсутствует или запись недоступна, применяй правила в текущем обсуждении и честно сообщи, что между сессиями они не сохранены. Не обещай долговременную память без проверенного файла или другого доступного механизма.

Оценки сохраняй, когда это нужно для запрошенного сравнения, последующего пересчёта или по просьбе пользователя. В новой редакции сохрани источник требований, правила/редакцию, работы и их основания, платформенную матрицу, допущения, `B/R/T`, условия диапазона и дату. Предыдущую оценку не затирай. Читай только относящуюся к текущему запросу историю. Обновление skill pack не должно изменять это хранилище.

## Пересчёт и сравнение с фактом

При уточнении пересчитай затронутые блоки и их зависимости, убери неприменимые прежние допущения и риски. Покажи прежние/новые часы, дельту и причину: изменение требований, обязательных проверок, матрицы, базы времени или реализовавшийся риск. Не пересчитывай несвязанные блоки без причины.

При получении фактических затрат сравни их с оценкой по тем же блокам и тем же границам. Раздели ошибку оценки, изменение объёма, реализовавшиеся риски, активную диагностику и календарное ожидание. Покажи использованную часть резерва отдельно от отклонения базы. Если известен только суммарный факт, сравни доступные итоги и запроси разбивку лишь для необходимого объяснения; не распределяй факт по блокам выдуманными долями.

Используй подтверждённые сопоставимые результаты как историю для будущих оценок в этой области. Объясняй отличия покрытия, окружения, документации, подготовки и сложности. Один завершённый пример не устанавливает универсальный норматив команды.
