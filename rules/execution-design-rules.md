# Макеты и визуальные проверки

Применять при тестировании frontend, mobile web, нативных приложений и других визуальных изменений, включая быстрые проверки компонентов и анализ присланных материалов. Для scope только backend/API макеты не требуются. Подготовка документации и сбор контекста сами по себе не запускают прогон.

## Получение и проверка источника

1. До проверок выяснить, какие макеты относятся к текущим экранам и состояниям: проверить ссылки и вложения задачи и связанных требований в заданном scope. Если макеты упомянуты без ссылки или их наличие неизвестно, запросить источник либо уточнить, предусмотрены ли они, по [правилам доступов](execution-access-rules.md).
2. Попытаться прочитать найденный макет доступным средством. Для Figma применять [профиль](../integrations/profiles/figma.md), включая браузерный fallback; для другого источника - просмотр или экспорт. Полный актуальный макет, уже полученный в этой задаче, использовать повторно без требования подключить интеграцию.
3. Убедиться, что видно содержимое нужного экрана, состояния и размера. URL, метаданные, успешное открытие или пустой canvas этого не подтверждают. Доступ к одному экрану не подтверждает остальные состояния. Снимок реализации не заменяет макет.

## Проверки без полного макета

- При отсутствующем, недоступном, неполном или неясном макете сразу назвать конкретный пробел и запросить доступ, подходящий экспорт или уточнение. Не откладывать запрос до отчёта. При новом пробеле во время прогона сохранить наблюдения и запросить недостающее тем же способом.
- Продолжать доступную сверку с прочитанными макетами, функциональные/API-проверки по требованиям и базовую визуальную оценку непокрытых состояний. Ожидать ответ только для зависимой сверки. Если пользователь явно требует сначала получить макеты или исключает часть проверок, соблюдать это решение; повторно согласовывать его не нужно.
- Без макета оценивать наблюдаемую пригодность страницы: читается ли текст, не обрезаны ли существенные данные и элементы, нет ли перекрытий, мешающих чтению или действию, доступны ли элементы управления и результат действия. Проверять применимые состояния и размеры в scope, не выдумывать обязательные брейкпоинты, отступы, цвета или состав элементов.
- Подтверждённое препятствие использованию фиксировать с доказательством и конкретным последствием. Субъективное предпочтение оформления не объявлять дефектом. Если ожидаемое поведение неоднозначно, запросить решение.
- Если пользователь подтвердил отсутствие макетов, выполнять проверки по требованиям и базовую визуальную оценку в запрошенном scope. Не требовать создания макетов. При частичных макетах сравнивать покрытые состояния с ними, а остальные оценивать по доступным критериям.
- Различать соответствие прочитанному макету и базовую визуальную оценку. Успешная оценка страницы не подтверждает непрочитанный дизайн. Не менять критерий исходной строки молча: сохранять отложенную сверку и результат доступной части по [правилам отчёта](execution-report-rules.md). Временное отсутствие ответа не исключает сверку из scope; по получении источника вернуться к ней.
