# Объём и режим выполнения

Применять в `execute-task-testing` для web/API, Android и iOS. Задача в трекере, изменение и Test Run необязательны. Текст чата, включая расшифрованное голосовое поручение, файлы и явно переданные шаги задают допустимый контекст.

## Выбор режима и границ

Выбирать по поручению; не просить пользователя назвать режим или скилл, если намерение понятно. Режимы можно сочетать в одном прогоне, сохраняя границы каждого.

| Поручение | Основа проверок и завершение |
| --- | --- |
| Проверить изменение | Требования и затронутые сценарии текущей задачи |
| Выполнить Test Run, кейсы или шаги | Переданный набор и его условия; завершение по всем выбранным пунктам и конфигурациям |
| Быстро проверить приложение, smoke | Короткий маршрут по названным разделам и критичным действиям с конкретными наблюдаемыми критериями |
| Провести регрессию | Указанный набор кейсов или определённые функции, сценарии и платформы; полнота относится только к этому набору |
| Исследовать раздел, поискать проблемы | Цель исследования, область и предел сессии: время, маршрут или конкретные риски |

- Установить приложение/сборку, окружение, роль, платформы, область и достаточное условие завершения из доступного контекста. Запрашивать только пробелы, которые меняют действия, ожидания или границы; не требовать Jira key, релиз или Test Run ради шаблона. Уже известные сведения повторно не спрашивать.
- При общем smoke без списка экранов осмотреть доступную навигацию и назвать небольшой маршрут по основным разделам перед проверками. Критерии соотнести с целью: приложение запускается, открывается нужный раздел, загрузка заканчивается, выбранный переход выполняется без падения. Не вводить числовые пороги времени или бизнес-правила без источника.
- «Полная регрессия всего приложения» без набора или определённых границ требует уточнения покрытия. Предложить конкретный ограниченный объём; независимые явно заданные проверки можно выполнять. Не подменять полную регрессию smoke-проходом и не объявлять её завершённой по нескольким экранам.
- Сохранять названные платформы и конфигурации отдельно: успех Android не подтверждает iOS. Для недоступной части применять [правила доступов](execution-access-rules.md), продолжая независимую доступную часть.

## Готовые сценарии и Test Run

- Переданные для выполнения актуальные кейсы и шаги использовать как рабочие критерии прогона. Не требовать отдельную задачу или аналитику, если условия, действия и ожидания достаточны. При конфликте, неоднозначности или признаках устаревания запросить конкретное правило; не менять ожидание под реализацию.
- По ссылке/ключу сохранённого run получить его состав и полное содержание выбранных кейсов через настроенный TMS. Не собирать релиз заново и не искать дополнительные кейсы в библиотеке. Названия без шагов и ожиданий не считать достаточным содержанием. При недоступности запросить точный экспорт или недостающие пункты.
- Сохранить ключ run, case ID, вариант/конфигурацию и ссылки на шаги в локальной привязке результатов. Один кейс может соответствовать нескольким строкам отчёта; не терять связь при группировке действий по состоянию экрана. Дополнительные наблюдения не подменяют результаты исходных кейсов.
- Итоговый статус кейса не выводить по единственному успешному шагу: учитывать все его обязательные проверки и условия. Отсутствующее ожидание или непроверенный шаг сохранять как пробел по [правилам отчёта](execution-report-rules.md); не придумывать соответствие статусов TMS.
- Выполнение run даёт отчёт по умолчанию. Явно запрошенные изменения состава, назначений или запись наблюдённых результатов выполняются через `manage-test-run` по [правилам сохранённого run](test-run-rules.md#existing-test-run-management). Не изменять исходные кейсы и не создавать новый run как побочный результат выполнения.

## Исследовательский проход

- Начать с короткого плана по известной цели. До первого проверочного действия обозначить область и предел сессии; при их существенной неопределённости уточнить недостающее. Не строить заранее полный перечень неизвестных сценариев.
- По мере исследования добавлять новые проверки внутри этой области с очередными номерами до их выполнения. Указывать конкретное основание: цель smoke/исследования, явное поручение, требование или проверяемое свойство навигации. Такое дополнение локального рабочего плана не требует отдельного одобрения каждого пункта. Сохранять прежние номера, критерии и результаты; изменение существующей строки, расширение области или опубликованного плана подчиняется [правилам исправления](task-execution-rules.md#исправление-чек-листа-во-время-тестирования).
- Наблюдаемую реализацию использовать для выбора следующего действия, не как доказательство правильности бизнес-правила. При неизвестном ожидании сохранить наблюдение и конкретный вопрос со статусом `ТРЕБУЕТ УТОЧНЕНИЯ`; не объявлять его дефектом или `OK`. Подтверждённый сбой оценивать по известному критерию независимо от неизвестной причины.
- Завершить по установленному пределу, сохранив результаты и открытые вопросы. Пройденный маршрут или истечение времени не подтверждают непроверенные сценарии. Не создавать постоянные кейсы, регрессионную модель или баги без отдельного запроса.
