# Структура набора мобильных автотестов

Применять при создании набора или изменении его структуры. Сначала использовать соглашения целевого проекта. Для нового набора брать схему ниже за основу и добавлять каталоги по мере необходимости. Она не требует отдельного фреймворка поверх Maestro.

## Репозиторий и слои

По умолчанию хранить исходники тестов в Git рядом с приложением в `.maestro/`. Если команда использует отдельный QA-репозиторий, сохранять эту схему размещения и связывать ревизию тестов с проверяемой сборкой. Конкретные тесты приложения в общий Testdocs Kit не добавлять.

```text
.maestro/
  config.yaml
  tests/
    catalog/
      add-to-favorites.yaml
  subflows/
    auth/
      login.yaml
    catalog/
      select-eligible-product.yaml
  selectors/
    catalog.js
  fixtures/
  scripts/
```

- `tests/` содержит самостоятельные пользовательские сценарии, сгруппированные по функциям продукта. Сценарий связывает подготовку, действие и проверку бизнес-результата. Давать файлам устойчивые имена по поведению; ключ кейса или ссылку на требование хранить по соглашению проекта.
- `subflows/` содержит повторяемые действия, навигацию и подготовку данных. У подшага должны быть понятные входы, результат и исходное состояние. Не скрывать основное ожидание сценария внутри общего входа в приложение. Выносить повторяющуюся логику, а не каждое одиночное нажатие.
- `selectors/` содержит общие селекторы по экранам или компонентам. При изменении элемента исправляется его определение в одном месте. Реальные различия Android/iOS выносить в платформенные файлы с одинаковыми именами полей; общий сценарий сохранять, пока совпадает поведение.
- `fixtures/` содержит только необходимые открытые постоянные данные из требований. Текущий список товаров и выбранные при прогоне ID сюда не сохранять. `scripts/` нужен для повторно используемой логики, которую неудобно выразить YAML. Использовать поддерживаемый runner синтаксис, не предполагать доступность Node.js-модулей внутри Maestro.

Различать самостоятельные тесты и вызываемые подшаги при discovery. Наборы smoke/regression выбирать тегами или конфигурацией, без копий одного сценария в разных папках. Конкретные настройки Maestro и загрузка селекторов описаны в [профиле runner](../integrations/profiles/mobile-test-runners.md#структура-и-параметры-maestro).

Для командного набора описать один путь к актуальным тестам из основной ветки и порядок добавления через ревью проекта. Для Android и iOS сохранять общий ключ кейса при разных flows. Предусмотреть выбор платформы, кейса и группы по соглашениям проекта. Если запрошенный сценарий отсутствует, сообщать об этом до запуска. Для тестов, меняющих аккаунт, передавать данные выбранного платформенного профиля и сверять активную учётную запись перед действием, если профиль задаёт её идентификатор.

## Физические устройства в командном запуске

В стартовом шаблоне предусмотреть запуск на физическом устройстве для каждой поддерживаемой проектом мобильной платформы. Для Android по USB использовать ADB и Maestro. Для iPhone по USB использовать HTTP API Appium с XCUITest и настроенным WebDriverAgent. Способы подключения и запуска сохранённого YAML описаны в [профиле runner](../integrations/profiles/mobile-test-runners.md).

Выбор кейса и группы работает одинаково для телефона и виртуального устройства. При запуске проверить выбранную цель и сообщить, что нужно подготовить, если она недоступна. Повторный запуск на другом устройстве выполняется только при явном выборе этой цели.

Готовность маршрута подтвердить прогоном сохранённого smoke-теста на физическом устройстве. Сверить сборку и целевое устройство в результате. Если проект публикует отчёты, открыть отчёт именно этого прогона и проверить результат по выбранному устройству.

## Переменные и настройки

У каждого общего значения должен быть один источник. Объединять значения по назначению и области действия; локальные данные одного сценария не превращать в общий изменяемый файл.

| Что хранится | Источник и область действия |
| --- | --- |
| Открытые общие настройки, предел поиска, общие значения по умолчанию | Конфигурация набора, без повторения по сценариям |
| App ID, адрес стенда, целевая платформа | Явно выбранный профиль запуска или параметры CI; сценарии используют имена параметров |
| Логин, пароль, токен, приватные настройки устройства | Приватное хранилище окружения или секреты CI вне исходников, клиентского конфига и отчётов |
| Общие селекторы | Модуль соответствующего экрана или компонента |
| Вход конкретного подшага | Его явные параметры, без скрытой зависимости от предыдущего теста |
| Выбранный товар, исходное состояние, созданные ID | Состояние текущего сценария в памяти runner, инициализируемое заново при каждом запуске |

Описать в документации целевого набора обязательные параметры, их источники и допустимые открытые значения по умолчанию, команды запуска и проверенные версии runner. Перед действиями проверить наличие обязательных параметров и выбранное окружение. Отсутствующий обязательный аккаунт или адрес стенда не заменять молча гостевым входом или другим окружением. Не перекрывать переданные параметры одноимёнными константами в подшагах. Механизм передачи значений должен работать и локально, и в выбранном CI.

Для динамических объектов применять [правила выбора данных](mobile-automation-rules.md#выбор-тестовых-данных). Отдельный файл с фиксированными ID не устраняет зависимость от случайных данных.

## Независимость и проверка изменений

- Каждый самостоятельный сценарий подготавливает своё состояние и запускается отдельно, без результатов предыдущего теста. Для параллельных запусков выделять независимые аккаунты или объекты, если сценарии меняют общие данные. Общий файл переменных не использовать для обмена состоянием между тестами.
- Повторный запуск должен учитывать изменения предыдущего. Восстанавливать только собственные изменения и только в рамках разрешённых действий; сохранять диагностику исходного сбоя, даже если очистка тоже завершилась ошибкой.
- Для нового сценария проверить запуск отдельно и в выбранном наборе. После изменения общего подшага, селектора или настройки запускать затронутые сценарии. Проверить discovery: служебные flows не запускаются как тесты, вложенные тесты обнаруживаются, фильтр выбирает ожидаемый набор, пустой прогон не считается успешным.
- Исходники и открытые настройки версионировать. Сборки, приватные файлы и результаты держать вне исходников; отчёты и доказательства - во внешнем workspace задачи. Для каждого прогона выделять отдельный каталог, фиксировать ревизию тестов, сборку, платформу и устройство. В CI сохранять код завершения и свежие материалы даже при ошибке.
