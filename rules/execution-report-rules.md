# Execution report

## Статусы отчёта

Использовать только следующие execution-статусы:

| Статус | Когда применять | Jira Wiki Markup |
| --- | --- | --- |
| `OK` | Весь пункт выполнен, результат полностью совпал с подтверждённым ожидаемым | `{color:#14892c}*OK*{color}` |
| `НЕ OK` | Наблюдается подтверждённое несоответствие | `{color:#d04437}*НЕ OK*{color}` |
| `ПОЧТИ OK` | Основной результат достигнут, но есть локальное подтверждённое отклонение, не позволяющее поставить `OK` | `{color:#6554c0}*ПОЧТИ OK*{color}` |
| `НЕ ПРОВЕРЕНО` | Проверка не выполнялась или отсутствует доступ/сборка/данные | `{color:#6b778c}*НЕ ПРОВЕРЕНО*{color}` |
| `ЧАСТИЧНО ПРОВЕРЕНО` | Выполнена только явно указанная часть пункта или матрицы | `{color:#bf6700}*ЧАСТИЧНО ПРОВЕРЕНО*{color}` |
| `ТРЕБУЕТ УТОЧНЕНИЯ` | Нет однозначного ожидаемого результата или источники конфликтуют | `{color:#0052cc}*ТРЕБУЕТ УТОЧНЕНИЯ*{color}` |

`ПОЧТИ OK` требует описания конкретного отклонения. `ЧАСТИЧНО ПРОВЕРЕНО` требует перечисления выполненной и оставшейся части. `НЕ ПРОВЕРЕНО` требует причины. Статус не заменяет фактический результат.

## Отчёт

- Выбрать способ выдачи до оформления отчёта. По умолчанию вернуть Jira Wiki отчёт в чате. Если пользователь запросил HTML-отчёт, оформить его по правилам ниже. При явно выбранной [прямой записи через API](checklist-delivery-rules.md#direct-api-delivery) отчётом служит сохранённый результат в назначении; локально достаточно структурированных записей и доказательств, без промежуточного HTML и дублирующей таблицы в чате. Отдельный HTML создавать только по запросу. Выбор формата сам по себе не разрешает внешнюю запись.
- Сохранить структуру и семь колонок исходного checklist. Заполнить `Фактический результат`, при необходимости `Комментарий`, и `Статус`.
- В фактическом результате указать только наблюдаемое. Ссылаться на доказательства по понятному имени или относительному пути внутри task workspace.
- `Комментарий` оставлять пустым, если нет отдельного полезного пояснения: причины ограничения, источника или ссылки на связанный дефект. Не дублировать результат и не переносить туда его доказательства. Всё необходимое для понимания факта, включая непроверенную часть, должно быть в `Фактическом результате`.
- Включать сохранённые доказательства успешных проверок `OK` вместе с доказательствами остальных результатов: они позволяют проверить работу агента. Требования ниже к описанию дефектов не ограничивают состав отчёта только неуспешными строками. Скриншоты прикреплять к соответствующим строкам после текста фактического результата.
- Для `НЕ OK` и `ПОЧТИ OK` указать ожидаемый источник, фактическое отклонение, окружение и доказательство. Не создавать Jira Bug автоматически; отдельный запрос маршрутизируется в `create-bug-report`.
- В конце кратко указать scope прогона, окружение/сборку, покрытые платформы и браузеры, ограничения, найденные несоответствия и оставшиеся вопросы.
- Публиковать результат только по явному запросу и через разрешённый канал. Для прямой записи через API передавать проверенные результаты по мере выполнения по правилам доставки; не откладывать всю запись до сборки отдельного отчёта.

### Язык результатов тестирования

- Применять раздел «Язык чек-листа» из `test-checklist-standard.md` также к фактическим результатам, комментариям, описаниям проблем, подписям скриншотов и итогам прогона. Писать естественным профессиональным языком тестировщика, без машинного протокола действий и повторяющихся служебных фраз.
- Фактический результат описывать коротко и предметно: что сделали, что произошло и, при наличии проблемы, чем это отличается от ожидаемого. Например: После нажатия "Сохранить" окно осталось открытым, изменения не сохранились. Это пример формулировки, а не готовое наблюдение для подстановки в отчёт.
- Вместо «зафиксировано несоответствие ожидаемому поведению компонента» назвать само отличие: Кнопка "Далее" неактивна после заполнения всех обязательных полей. Не добавлять предположения о причине ошибки к наблюдаемому факту.
- Ограничения объяснять обычными словами с конкретной причиной: «Не удалось проверить оплату: нет доступа к тестовому аккаунту». Название инструмента или техническую ошибку приводить только если это помогает восстановить доступ или понять границы проверки; не заполнять ими каждую строку.
- Чтение кода или содержимого сборки не подтверждает результат выполнения UI/API-проверки. Если индикатор загрузки не удалось увидеть, так и написать; не заменять наблюдение описанием переменной загрузки. Если тело запроса не получено, явно указать, что его поля не проверены; описание сериализации этого не меняет. Для целиком неподтверждённого критерия использовать `НЕ ПРОВЕРЕНО`; `ЧАСТИЧНО ПРОВЕРЕНО` - только когда часть критериев действительно проверена при выполнении. Краткую пометку "По коду обработка предусмотрена" добавлять лишь как отдельное пояснение, если это полезно для продолжения.
- В итогах кратко написать, что проверено, какие проблемы найдены и что осталось проверить. Ссылки на требования и доказательства сохранять по правилам ниже. Естественный стиль не меняет источник наблюдения: проверку по присланному скриншоту или видео так и обозначать, не выдавая её за выполненные действия в приложении.

### Понятное и подтверждённое описание несоответствий

- Для каждого несоответствия описать одну сопоставимую пару: что должно происходить по конкретному требованию и что наблюдалось при тех же условиях. Назвать экран или элемент, действие или состояние и точное отличие простым языком. Читатель должен определить проблему по ячейкам `Ожидаемый результат` и `Фактический результат`, без догадок и поиска объяснения в комментариях. Формулировки «не соответствует требованиям», «сломана вёрстка» или «работает неправильно» без конкретного отличия недостаточны.
- В `Ожидаемый результат` включить понятный критерий и подтверждение: короткий точный фрагмент реального требования с именованной кликабельной ссылкой на конкретный пункт, раздел, комментарий или узел макета. Если прямой якорь недоступен, дать ссылку на документ и точное название раздела/номер пункта для поиска. Не придумывать цитаты, ссылки, номера пунктов, ограничения или ожидаемое поведение. Не выдавать собственный пересказ за дословную цитату.
- Текст требования с точной ссылкой достаточен для текстового основания: скриншот требования необязателен. Если он полезнее, приложить читаемый снимок релевантного фрагмента с той же ссылкой и подписью после текста ожидаемого результата. Это не отменяет правила включения изображения макета при запрошенном визуальном сравнении в HTML.
- В `Фактический результат` описать наблюдаемое поведение и явно назвать расхождение с указанным критерием. Для видимого UI-несоответствия приложить после полного текста скриншот, на котором видно именно это расхождение, с подписью о подтверждаемом факте. Общий снимок страницы, не показывающий проблему, не считается её подтверждением. Если различие проявляется только в переходе или во времени, дополнить снимки последовательностью состояний или видео; для API/данных использовать релевантный ответ, лог или другое непосредственное доказательство, а не имитировать визуальное подтверждение.
- Если скриншот недоступен или не фиксирует заявленный факт, явно указать пробел и доступное доказательство; не утверждать, что несоответствие подтверждено скриншотом. Отделять наблюдаемый результат от предположений о причине. Недостаток доказательств учитывать при выборе статуса по правилам выше.
- Если ожидаемое поведение не найдено в доступных требованиях, неоднозначно или противоречит другому актуальному источнику, описать наблюдение и вынести ожидаемое правило в `ТРЕБУЕТ УТОЧНЕНИЯ`; не объявлять дефектом отличие от предположения агента. Ни текущий, ни предыдущий checklist сам по себе не заменяет подтверждённое требование.
- Перед выдачей для каждого `НЕ OK` и `ПОЧТИ OK` проверить цепочку: конкретный источник → подтверждённый ожидаемый результат → наблюдаемое отличие → доказательство этого отличия. Удалить неподтверждённые утверждения или явно обозначить их как вопросы, не скрывая реально наблюдавшиеся факты.

### Текст и изображения в ячейках

- В ячейке `Фактический результат` сначала разместить весь текст наблюдения законченными предложениями или абзацами, затем отдельный блок доказательств с изображениями и короткими подписями. Изображения остаются в той же ячейке, но не вставляются внутрь слова, предложения, абзаца или между частями описания. После начала блока изображений допускаются только подписи и ссылки, а не продолжение основного текста результата.
- Скриншоты выполнения и их подписи относятся к `Фактическому результату` той же строки при любом статусе. Не помещать их в `Комментарий` или отдельную строку. Изображения требований/макета относятся к `Ожидаемому результату`. Если нужную ячейку нельзя однозначно определить, уточнить привязку, а не использовать колонку комментариев как запасную.
- Несколько скриншотов расположить после текста в порядке описанных состояний; подписать, какое состояние или наблюдение подтверждает каждый. При необходимости сослаться на номера скриншотов из текста. Не вставлять дубли ради количества.
- В HTML использовать отдельные блочные элементы для текста и каждого изображения, например `<p>` и `<figure>` с `<figcaption>`. Изображения выводить с `display: block; max-width: 100%; height: auto`, без обтекания текста и абсолютного позиционирования. Подпись и `alt` должны отличать источник и состояние. Размер миниатюры не должен растягивать колонку; дать возможность открыть читаемый оригинал.
- При вставке через редактор сначала полностью заполнить текст ячейки, затем создать отдельный блок в её конце и вставить изображения туда. Не полагаться на сохранённую позицию курсора или символьные смещения после предыдущих вставок.
- Для Jira Wiki сохранять правила синтаксиса таблицы: не добавлять сырой HTML; физические переносы внутри блока кода допустимы только по подтверждённому контракту назначения из [профиля QA Report](../integrations/profiles/qa-report.md#код-в-ячейках). Представление доказательств выбирать по возможностям назначения, сохраняя порядок «полный текст → данные → изображения». Небольшие текстовые данные при доставке оформлять по [правилам данных и вложений](checklist-delivery-rules.md#текстовые-данные-и-вложения). Не считать, что Jira-import автоматически поддерживает HTML и вложения.
- В переносимом HTML изображения должны открываться у получателя: использовать включённые в документ данные изображений, поставляемую вместе с HTML папку с относительными путями либо поддержанные назначением вложения/URL. Пути к временному файлу или `file://` на компьютере автора не являются доставленным изображением. Не загружать доказательства во внешний сервис без запроса на этот способ доставки.
- Для запрошенного HTML перед выдачей открыть готовый файл, а после разрешённой вставки через UI осмотреть результат в редакторе, если доступен просмотр. Проверить целостность текста, положение и загрузку изображений именно в `Фактическом результате`, подписи, сохранность колонок и читаемость оригиналов. При прямой записи через API выполнить компактную сверку по правилам доставки вместо обязательного обхода редактора. Не объявлять вёрстку проверенной по исходному HTML или receipt.

Порядок внутри ячейки (схема, не готовые данные отчёта):

```text
Фактический результат:
  Полный текст всех наблюдений и отклонений.
  Факт - скриншот 1: <состояние экрана>.
  Факт - скриншот 2: <другое подтверждаемое состояние>.
```
