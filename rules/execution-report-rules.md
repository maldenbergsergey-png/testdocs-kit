# Execution report

## Статусы отчёта

Использовать только следующие execution-статусы:

| Статус | Когда применять | Jira Wiki Markup |
| --- | --- | --- |
| `OK` | Весь пункт выполнен, результат полностью совпал с подтверждённым ожидаемым | `{color:#14892c}*OK*{color}` |
| `НЕ OK` | Подтверждённое несоответствие, кроме явно тривиального замечания, исправление которого необязательно | `{color:#d04437}*НЕ OK*{color}` |
| `ПОЧТИ OK` | Только тривиальное замечание без влияния на использование и понимание результата; его допустимо оставить без исправления | `{color:#6554c0}*ПОЧТИ OK*{color}` |
| `НЕ ПРОВЕРЕНО` | Проверка не выполнялась или отсутствует доступ/сборка/данные | `{color:#6b778c}*НЕ ПРОВЕРЕНО*{color}` |
| `ЧАСТИЧНО ПРОВЕРЕНО` | Выполнена только явно указанная часть пункта или матрицы | `{color:#bf6700}*ЧАСТИЧНО ПРОВЕРЕНО*{color}` |
| `ТРЕБУЕТ УТОЧНЕНИЯ` | Нет однозначного ожидаемого результата или источники конфликтуют | `{color:#0052cc}*ТРЕБУЕТ УТОЧНЕНИЯ*{color}` |

`ПОЧТИ OK` требует конкретного замечания. Работа основного сценария, локальность или простота исправления сами по себе не основание для этого статуса: отсутствие нужного элемента, неверное значение, нарушение поведения или существенное отличие от макета - `НЕ OK`. Если необязательность исправления неясна, подтверждённое несоответствие - `НЕ OK`. Неполная проверка не становится `ПОЧТИ OK`. Для `ЧАСТИЧНО ПРОВЕРЕНО` указать наблюдавшуюся часть в факте, оставшуюся часть - в комментарии; для `НЕ ПРОВЕРЕНО` оставить факт пустым, причину указать в комментарии.

Неизвестная причина ошибки не означает неизвестного ожидания: при подтверждённом требовании и выполненных условиях наблюдаемое нарушение - `НЕ OK`. Значение флага API само по себе не доказывает ограничение тестовых данных и не меняет критерий UI-проверки. Если неизвестно, как этот флаг влияет на применимость требования, задать конкретный вопрос со статусом `ТРЕБУЕТ УТОЧНЕНИЯ`; если обязательное условие известно, но подходящих данных нет, использовать `НЕ ПРОВЕРЕНО` либо `ЧАСТИЧНО ПРОВЕРЕНО` по реально выполненной части.

Эти статусы описывают результат, а не разрешают пропуск. Перед оставлением проверки из-за недоступности применить [правила доступов](execution-access-rules.md): запросить недостающее, выполнить доступную часть и сохранить ожидающую ответа зависимость. До ответа результат по ней промежуточный; не объявлять весь запрошенный прогон завершённым. Базовую визуальную оценку без макета не выдавать за подтверждение соответствия ему.

## Отчёт

- Выбрать способ выдачи до оформления отчёта. По умолчанию вернуть Jira Wiki отчёт в чате. Если пользователь запросил HTML-отчёт, оформить его по правилам ниже. При явно выбранной [прямой записи через API](checklist-delivery-rules.md#direct-api-delivery) отчётом служит сохранённый результат в назначении; локально достаточно структурированных записей и доказательств, без промежуточного HTML и дублирующей таблицы в чате. Отдельный HTML создавать только по запросу. Выбор формата сам по себе не разрешает внешнюю запись.
- Сохранить структуру и семь колонок исходного checklist. Заполнить `Фактический результат`, при необходимости `Комментарий`, и `Статус`; для найденной ошибки дополнить `Как проверить` шагами воспроизведения по правилам ниже.
- В фактическом результате указать только наблюдаемое поведение и непосредственно подтверждающее его доказательство. Имена файлов должны быть понятными; локальные пути нужны лишь для локального отчёта, а не как текст поведения.
- В `Комментарий` помещать именованные ссылки на использованные требования/макеты с указанием пункта, ссылку на связанный дефект и при необходимости одно короткое пояснение: существенный пробел выполнения, конкретный вопрос по требованию, пояснение к исходному API-запросу/ответу или метку подтверждённого компонента. Не дублировать результаты и не переносить сюда расследование, скриншоты или ответы API. Без источника или полезного пояснения комментарий пуст.
- Включать сохранённые доказательства `OK` вместе с остальными выполненными результатами. Скриншоты факта и ожидания размещать в соответствующих ячейках после текста по [правилам доказательств](execution-evidence-rules.md).
- Для `НЕ OK` и `ПОЧТИ OK` дать сопоставимые ожидание и факт с доказательствами; источник - в комментарии, общее окружение - один раз в сведениях о прогоне. Не создавать Jira Bug автоматически; отдельный запрос маршрутизируется в `create-bug-report`.
- Общие сведения оформлять по [правилам кратких вводных](#краткие-вводные): только окружение и существенные общие ограничения. Результаты, проблемы и вопросы оставлять в соответствующих строках.
- Общий вердикт "OK / НЕ OK", сводку дефектов и счётчики статусов по умолчанию не добавлять: результаты уже видны в чек-листе. Отдельный итог нужен только по явному запросу или обязательному контракту назначения; наличие поля "Итог" само по себе не требует его заполнения.
- Публиковать результат только по явному запросу и через разрешённый канал. Для прямой записи через API передавать проверенные результаты по мере выполнения по правилам доставки; не откладывать всю запись до сборки отдельного отчёта.

### Краткие вводные

- В QA Report поле "Окружение" (стенд) содержит только короткое обозначение: `DEV`, `STAGE`, `PROD` или подтверждённое короткое имя другого стенда. Не дописывать туда URL, приложение, сборку, устройство, размеры или результаты. Не угадывать категорию по адресу; неизвестный стенд не заменять значением по умолчанию редактора. При подготовке неизвестное значение оставлять незаполненным, а уточнение давать отдельно пользователю, не текстом поля; существующие значения сохранять по правилам доставки.
- "Вводные данные" - обычно 1-2 короткие строки: окружение клиента и, если нужно, существенное общее ограничение запрошенных проверок. Если полезных сведений нет, оставить поле пустым. Не заполнять его ради объёма.
- Для мобильного приложения: iOS/Android, известная версия ОС, версия/номер сборки и устройство, например `iOS 18; сборка 42; iPhone 16, симулятор`. Размер экрана с единицами добавлять только если он важен для проверки; разрешение скриншота не дублировать. Неизвестные значения опускать, не запрашивать их ради заполнения вводных.
- Для web: браузер и известная версия, например `Chrome 128`. При явном соглашении об актуальной версии достаточно `Chrome, последняя версия`; без него не выдавать неизвестную версию за последнюю. Не выяснять номер только ради отчёта. Для адаптива указывать фактически проверенные ширины: `Chrome 128; ширины 1440, 768, 375 px`. Это пример, не обязательный набор. Высоту, DPR, разрешение снимков и остальные параметры добавлять только если они влияют на проверку. В плане обозначать целевые ширины, не выдавая их за выполненный прогон.
- Общий способ проверки, ограничение или сложность указывать одной короткой фразой, только если это касается всего прогона и влияет на понимание результата. Не повторять причины отдельных непроверенных строк и уже описанные в них проблемы. Общую причину можно указать один раз во вводных; в строках сохранять статусы без её пересказа. Если ограничений нет, не писать "Ограничений нет". Решение из источника передавать как существенную границу покрытия, без автора, даты и обсуждения. Исключённые из задания проверки не перечислять.
- Не включать во вводные описание задачи, ход и дату прогона, общий итог, список дефектов, счётчики статусов, перечень источников, историю согласований и технический протокол. Источники и вопросы относятся к комментариям строк; не переносить лишнюю сводку в отдельный раздел или поле ради обхода этого правила. Краткость вводных не отменяет полноту строк и доказательств.
- Ссылки на задачу/стенд размещать по [правилам доставки](checklist-delivery-rules.md); если канал требует ссылки в содержимом, оставить только необходимые именованные ссылки без поясняющего абзаца. Не повторять доступные отдельные поля.

### Язык результатов тестирования

Применять [общие критерии качества](core.md#качество-всех-qa-артефактов). Ориентир для факта - 1-2 коротких предложения; это не ограничение на нужные доказательства и существенные условия.

- В факте назвать наблюдаемое поведение или отличие. При необходимости дать один показательный пример: "Цены идут не по возрастанию: после 10 700 000 показано 7 600 000". Не пересказывать шаги, ожидание, причину статуса, другие проверки и расследование. Не добавлять общую оценку после конкретного результата.
- После перепроверки заново собрать факт, комментарий и статус строки по актуальным наблюдениям, а не дописывать блок "Дополнительная проверка" с датой и историей попыток. Сохранить существенные различия ролей, данных и состояний; не выдавать последнее наблюдение за результат всех условий. Предыдущие наблюдения, даты, перечни объектов и диагностику хранить в workspace задачи с привязкой доказательств; в строке оставлять только необходимые для её критерия сведения и материалы. Перепроверка не разрешает затирать исходные доказательства.
- Описывать состояние приложения, а не снимок или процесс его получения: "В открытой карточке сделки на Android баннер не отображается" вместо "На снимке Android баннера нет". В факте, ожидании и комментарии не писать "на скриншоте", "по кадрам", "на момент съёмки" и подобные обороты. Не заменять их формальным "на момент проверки". При сравнении платформ назвать существенную разницу условий: "На iOS и Android открыты разные сделки; одинаковое состояние оплаты не подтверждено". Наблюдение одной карточки не обобщать на все сделки или платформу; не предполагать устаревшее состояние или причину отсутствия баннера. Время после действия сохранять, если оно относится к поведению продукта, например "Через 30 секунд после оплаты баннер остаётся видимым".
- В комментарии оставить источник и, если нужно, краткое ограничение, вопрос, ссылку на дефект/основной пункт или подтверждённую метку компонента. Без полезного дополнения ячейка пустая. Не повторять факт и не добавлять фразы "замечаний нет", "результат подтверждён", версии причины, прежние статусы или описание приложенных файлов. В готовые ячейки не включать инструкции вроде "разместить снимок после текста": перенос вложений - отдельное действие, а не текст отчёта.
- Писать от лица автора отчёта без рассказа о том, кто заказал или выполнил проверку. Не переносить в поля пересказ задания: "Запрос пользователя: нефункциональная проверка экранов быстрого входа", "по вашему запросу", "пользователь попросил". Не заменять его фразами "по запросу" или "мной выполнена проверка". Ссылка "Требование из чата" уместна для конкретного правила поведения, но не для повторения темы задания. "Пользователь" допустим как роль в продукте, если это нужно для сценария.
- Описывать простые действия и видимый результат: "При повороте телефона горизонтально нижние кнопки не видны". В факт и комментарий не переносить служебную подготовку, уборку и возврат тестовой среды в исходное состояние: "Портретная ориентация восстановлена", "сессия завершена". Если возврат сам входит в критерий, назвать, что изменилось: после поворота телефона обратно кнопка "Продолжить" снова видна. Не убирать нужные размеры, термины и условия только ради разговорного текста; нужную подготовку в воспроизведении и очистку в постусловиях кейса сохранять.
- Успешная ручная пересортировка не отменяет ошибку исходного порядка. Если оба сценария запрошены, у каждого своя строка. Не добавлять строки для диагностических действий и не менять критерии ради оформления. Одна строка сохраняет одну связную проверку по [стандарту чек-листа](test-checklist-standard.md#одна-строка--одна-связная-проверка).
- Для UI описывать экран; сетевые параметры и ID оставлять в доказательствах, если они не нужны для понимания критерия. Для API сохранять нужные метод, адрес, код и поле. Различать "запрос приложения" и "отдельный запрос к API"; не выдавать ручной запрос за запрос приложения. Служебные названия "QA-запрос" и "агентский запрос" не нужны.
- Метку `BE` в комментарии frontend/mobile-строки ставить только при подтверждённой серверной причине: например, корректный запрос приложения получил ответ, нарушающий контракт. Ошибка отдельного запроса с неверными параметрами этого не доказывает. Без подтверждения метку и оговорки о виновности не добавлять. Метка не меняет статус и не требует новой строки или колонки.
- Ненаблюдавшийся индикатор или неполученное тело запроса - пробел в комментарии. Чтение кода не подтверждает выполнение UI/API-проверки. Полностью ненаблюдавшийся критерий - `НЕ ПРОВЕРЕНО` с пустым фактом; `ЧАСТИЧНО ПРОВЕРЕНО` допустимо лишь для действительно проверенной части. Не путать отсутствие наблюдения с наблюдением отсутствия.
- Общие ограничения указывать один раз во вводных; частные - в комментарии строки. Исходные файлы, время захвата и привязку источника к строке хранить в индексе доказательств, не пересказывать в тексте результата или комментария. Отсутствие самостоятельного прогона обозначать один раз во вводных: "Самостоятельный прогон приложения не выполнялся"; в смешанном отчёте назвать соответствующие строки. Блокировку объяснять прямо: "Нет тестового аккаунта для оплаты". Историю диагностики хранить в workspace задачи. Исправление ранее опубликованного ошибочного вывода сообщать пользователю отдельно от строк отчёта.

Писать нейтрально о продукте и результате, без рассказа об исполнителе. Заметки "агент не досмотрел видео", "инструмент не успел", "не дочитал ответ" и протокол незавершённых попыток в чек-лист не переносить. Существенную недоступность данных выразить по сути, например "Состояние после перезапуска приложения не проверено" или "Нет макета для сравнения", либо сообщить пользователю отдельно, если это вопрос продолжения работы. Сохранить честный статус и происхождение наблюдения; не приписывать невыполненный прогон тестировщику.

### Повтор одного дефекта

- Полные дубли одной проверки с одинаковыми условиями и критерием убирать при подготовке плана. Ссылки ниже нужны, когда отдельные обоснованные проверки выявили один дефект; они не оправдывают дублирование самих проверок.
- Если в нескольких выполненных проверках подтверждён один и тот же дефект, выбрать основной пункт и один раз описать в нём шаги воспроизведения, отличие и доказательства. В остальных фактах достаточно "Та же ошибка, см. пункт 3" с точным номером основного пункта. Использовать ссылку на строку или баг, если назначение поддерживает её и точный адрес известен.
- Сохранять отдельные проверки, ожидания и статусы. Для отсылки достаточно одинакового наблюдаемого нарушения при сопоставимых условиях; знать внутреннюю причину не требуется. Нужные отличия условий кратко дописать возле ссылки. Разные симптомы или независимые дефекты описываются отдельно, даже если предполагается общая причина.
- Ссылка подтверждает результат только для реально проверенного повторения. Не переносить `НЕ OK` на непроверенную строку по аналогии; оставить ей соответствующий статус. Основной пункт должен содержать полное описание, без цепочки ссылок и круговых отсылок. При смене нумерации обновить ссылки.
- Повторно использовать подходящие доказательства без копий файлов и повторных загрузок. Сохранять привязку каждой проверенной строки к доказательству в индексе; отличающееся состояние подтверждать собственным материалом.

### Понятное и подтверждённое описание несоответствий

- Для каждой отдельной ошибки на любой поверхности, включая `НЕ OK` и тривиальное замечание `ПОЧТИ OK`, записать понятные нумерованные шаги воспроизведения в `Как проверить` основного пункта. Повторения оформлять по [правилу одного дефекта](#повтор-одного-дефекта). Начать с известного исходного состояния, назвать нужные данные и действия по порядку: `1. Открыть ...; 2. Выбрать ...; 3. Нажать ...`. Для UI использовать названия экранов и элементов; для API, данных и интеграций - необходимые метод, адрес, параметры и действие проверки. Не подменять шаги историей инструментов или расследования и не добавлять ненаблюдавшиеся переходы. Если путь известен лишь частично, записать подтверждённую часть, а пробел кратко отметить в комментарии.
- Краткий способ проверки достаточен для исходного плана и успешной строки; найденная ошибка требует последовательности, по которой коллега сможет повторить её без устных пояснений. Сохранять исходный критерий и условия: уточнение воспроизведения не разрешает менять ожидание под реализацию. Не создавать отдельный тест-кейс или баг автоматически. Если таблица назначения предусматривает отдельное поле шагов, использовать его без дублирования и добавления колонок в стандартный чек-лист. В Jira сохранять одну физическую строку таблицы, разделяя нумерованные действия точками с запятой; настоящий список использовать только при подтверждённой поддержке внутри ячейки.
- Для каждого несоответствия описать одну сопоставимую пару: что должно происходить по конкретному требованию и что наблюдалось при тех же условиях. Назвать экран или элемент, действие или состояние и точное отличие простым языком. Читатель должен определить проблему по ячейкам `Ожидаемый результат` и `Фактический результат`, без догадок и поиска объяснения в комментариях. Формулировки «не соответствует требованиям», «сломана вёрстка» или «работает неправильно» без конкретного отличия недостаточны.
- В `Ожидаемый результат` включить краткое само требование: что должно произойти при этих условиях. Сохранить пригодную формулировку источника и слова, по которым её можно найти; не придумывать ограничения или цитаты. Ссылку на конкретный пункт, раздел, комментарий или узел макета поместить в `Комментарий`. Если якоря нет, дать там ссылку на документ и точное название раздела. Список критериев использовать лишь при необходимости.
- Когда возможно, дополнить ожидание читаемым снимком соответствующего фрагмента требования или макета по [правилам доказательств](execution-evidence-rules.md), независимо от формата отчёта. Для визуального дефекта показать сопоставимые изображения ожидания и факта в одной строке. Для других поверхностей использовать доступные примеры из контракта, исходные запросы/ответы, логи или видео, которые подтверждают отличие и помогают воспроизвести проблему. Материалы относятся к соответствующим ячейкам ожидания и факта. Текст должен объяснять отличие и без открытия документа; ссылка и изображение его не заменяют.
- В `Фактический результат` описать наблюдаемое поведение и явно назвать расхождение с указанным критерием. Для видимого UI-несоответствия приложить после полного текста скриншот, на котором видно именно это расхождение, с подписью о подтверждаемом факте. Общий снимок страницы, не показывающий проблему, не считается её подтверждением. Если различие проявляется только в переходе или во времени, дополнить снимки последовательностью состояний или видео; для API/данных использовать релевантный ответ, лог или другое непосредственное доказательство, а не имитировать визуальное подтверждение.
- Для backend/API после краткого факта привести реально полученное тело ответа по [правилам подлинности](execution-evidence-rules.md#реальные-ответы-бэкэнда): небольшой ответ целиком в блоке кода, большой исходным файлом с дословным фрагментом при необходимости. Статус, проблемное поле и вывод описать вне тела; не собирать собственный JSON-доказательство. Ожидание должно называть соответствующее поле/значение или действие из контракта. Не добавлять нерелевантные ответы и сопутствующие логи; правила переноса данных - в [доставке](checklist-delivery-rules.md#текстовые-данные-и-вложения).
- Если снимок недоступен или не фиксирует факт, указать существенный пробел в комментарии и использовать доступное непосредственное доказательство. Не утверждать подтверждение непригодным снимком и не подменять факт гипотезой. Недостаток доказательств учитывать при выборе статуса.
- Если ожидаемое поведение не найдено в доступных требованиях, неоднозначно или противоречит другому актуальному источнику, описать наблюдение и вынести ожидаемое правило в `ТРЕБУЕТ УТОЧНЕНИЯ`; не объявлять дефектом отличие от предположения агента. Ни текущий, ни предыдущий checklist сам по себе не заменяет подтверждённое требование.
- Перед выдачей для каждого `НЕ OK` и `ПОЧТИ OK` проверить цепочку: конкретный источник → подтверждённый ожидаемый результат → шаги воспроизведения → наблюдаемое отличие → доказательство этого отличия. Удалить неподтверждённые утверждения или явно обозначить их как вопросы, не скрывая реально наблюдавшиеся факты.
- Перечитать ожидание и факт без комментария и вложений: понятно ли отличие? Для повторения дефекта проверить точную отсылку к полному описанию в основном пункте. Затем убрать из комментария повторы и диагностический пересказ. Ориентир 1-2 предложения относится к описанию, а не к исходным данным или существенным ограничениям.

### Текст и изображения в ячейках

- В ячейке `Фактический результат` сначала разместить весь текст наблюдения законченными предложениями или абзацами, затем отдельный блок доказательств с изображениями и короткими подписями. Изображения остаются в той же ячейке, но не вставляются внутрь слова, предложения, абзаца или между частями описания. После начала блока изображений допускаются только подписи и ссылки, а не продолжение основного текста результата.
- Скриншоты выполнения и их подписи относятся к `Фактическому результату` той же строки при любом статусе. Не помещать их в `Комментарий` или отдельную строку. Изображения требований/макета относятся к `Ожидаемому результату`. Если нужную ячейку нельзя однозначно определить, уточнить привязку, а не использовать колонку комментариев как запасную.
- Несколько скриншотов расположить после текста в порядке описанных состояний; подписать, какое состояние или наблюдение подтверждает каждый. При необходимости сослаться на номера скриншотов из текста. Не вставлять дубли ради количества.
- В HTML использовать отдельные блочные элементы для текста и каждого изображения, например `<p>` и `<figure>` с `<figcaption>`. Изображения выводить с `display: block; max-width: 100%; height: auto`, без обтекания текста и абсолютного позиционирования. Подпись и `alt` должны отличать источник и состояние. Размер миниатюры не должен растягивать колонку; дать возможность открыть читаемый оригинал.
- При вставке через редактор сначала полностью заполнить текст ячейки, затем создать отдельный блок в её конце и вставить изображения туда. Не полагаться на сохранённую позицию курсора или символьные смещения после предыдущих вставок.
- Для Jira Wiki сохранять правила синтаксиса таблицы: не добавлять сырой HTML; физические переносы внутри блока кода допустимы только по подтверждённому контракту назначения из [профиля QA Report](../integrations/profiles/qa-report.md#код-в-ячейках). Представление доказательств выбирать по возможностям назначения, сохраняя порядок «полный текст → данные → изображения». Небольшие текстовые данные при доставке оформлять по [правилам данных и вложений](checklist-delivery-rules.md#текстовые-данные-и-вложения). Не считать, что Jira-import автоматически поддерживает HTML и вложения.
- В переносимом HTML изображения должны открываться у получателя: использовать включённые в документ данные изображений, поставляемую вместе с HTML папку с относительными путями либо поддержанные назначением вложения/URL. Пути к временному файлу или `file://` на компьютере автора не являются доставленным изображением. Не загружать доказательства во внешний сервис без запроса на этот способ доставки.
- Для запрошенного HTML перед выдачей открыть готовый файл, а после разрешённой вставки через UI осмотреть результат в редакторе, если доступен просмотр. Проверить целостность текста, положение и загрузку изображений именно в `Фактическом результате`, подписи, сохранность колонок и читаемость оригиналов. При прямой записи через API выполнить компактную сверку по правилам доставки вместо обязательного обхода редактора. Не объявлять вёрстку проверенной по исходному HTML или receipt.

Порядок внутри ячейки (схема, не готовые данные отчёта):

```text
Фактический результат:
  Краткое наблюдаемое поведение и конкретное отклонение, если оно есть.
  Факт - скриншот 1: <состояние экрана>.
  Факт - скриншот 2: <другое подтверждаемое состояние>.
```
